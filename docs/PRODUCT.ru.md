# Продукт

> Статус: **Предложено** (Phase 0) — ожидает утверждения владельцем. Язык: [English](PRODUCT.md) · Русский
>
> Связанные документы: [ARCHITECTURE](ARCHITECTURE.ru.md) · [ROADMAP](ROADMAP.ru.md) · [DECISIONS](DECISIONS.ru.md)

## 1. Видение

> **«От голой инфраструктуры до готового к продакшену кластера Kubernetes при минимальном участии пользователя».**

**Farvater** — это одна платформа, одна модель конфигурации и один движок развёртывания. Она разворачивает полностью подготовленный кластер Kubernetes практически в один клик, а затем продолжает им управлять.

Идеальный результат для отдельного пользователя: *«Я выбираю Production + мои серверы (или Hetzner) + Medium → нажимаю Deploy → через некоторое время получаю полностью готовый, защищённый, наблюдаемый, обеспеченный резервными копиями и управляемый кластер Kubernetes».*

Идеальный результат для компании (Enterprise): *«Мы централизованно управляем сотнями кластеров Kubernetes, политиками, доступом, безопасностью, доказательствами соответствия требованиям, резервными копиями, обновлениями и инфраструктурой из единой панели управления (control plane)».*

Ключевой принцип — **скрывать сложность Kubernetes от пользователей, которым она не нужна, и никогда не ограничивать тех, кому нужен полный контроль.** Просто по умолчанию, мощно при необходимости.

## 2. Для кого

| Персона | Потребности | Основной режим |
|---|---|---|
| **Разработчик / небольшая команда** без глубоких знаний Kubernetes | Работающий защищённый кластер на своих серверах или VPS без изучения kubeadm, CNI, Helm, cert-manager… | Auto, Simple |
| **DevOps / SRE-инженер** | Воспроизводимая и объяснимая сборка кластеров с полным контролем над компонентами, версиями и YAML; автоматизация жизненного цикла (обновления, масштабирование, резервное копирование) | Advanced, YAML, CLI |
| **Платформенная команда** | Шаблоны, стандарты и самообслуживание для внутренних команд; много кластеров; автоматизация через API/CLI/Terraform | Шаблоны, API, Enterprise |
| **Специалист по безопасности / комплаенсу** (Enterprise) | Политики, применяемые до развёртывания, согласования, аудит, доказательства, оценка защищённости (posture) | Корпоративное управление Enterprise (governance) |
| **Администратор Enterprise** | SSO, RBAC/ABAC, тенантность, квоты, бюджеты, изолированные (air-gapped) установки | Enterprise |

## 3. Что может делать пользователь (основные возможности)

Из спецификации продукта (промпт §1):

1. Выбрать тип инфраструктуры: сначала bare metal / существующие серверы по SSH, затем VPS и облачные провайдеры.
2. Выбрать версию Kubernetes (из каталога поддерживаемых совместимых версий).
3. Выбрать топологию: один узел, стандартная, высокая доступность, критически важная (mission critical).
4. Выбрать сеть (CNI): Cilium, Calico, Flannel.
5. Выбрать хранилище: local-path, NFS, Longhorn, Ceph, облачный CSI.
6. Выбрать ingress на базе **Kubernetes Gateway API**: Cilium Gateway, Envoy Gateway, NGINX Gateway Fabric, Traefik.
7. Выбрать наблюдаемость: метрики, логи, трейсы (пресеты Basic / Standard / Full).
8. Выбрать компоненты безопасности: Pod Security, NetworkPolicies, cert-manager, журналирование аудита, усиленный (hardened) профиль.
9. Выбрать резервное копирование: снимки etcd, ресурсы Kubernetes, постоянные тома (persistent volumes) — в S3/MinIO/NFS/облачное хранилище.
10. Выбрать дополнительные компоненты из каталога аддонов.
11. Просмотреть конфигурацию в виде **плана** (пробный прогон, dry run) с diff, предупреждениями, оценкой времени и стоимости (если провайдер публикует цены).
12. Нажать **Deploy Cluster**.
13. Следить за развёртыванием в реальном времени: дерево задач и живые структурированные логи.
14. Получить полностью рабочий кластер, проходящий проверки состояния (health checks).
15. Скачать kubeconfig (привязанный к пользователю, по умолчанию краткоживущий).
16. Управлять кластером после создания с его дашборда.
17. Обновлять Kubernetes с помощью советника по обновлению (upgrade advisor).
18. Добавлять и удалять аддоны.
19. Масштабировать кластер.
20. Выполнять резервное копирование и восстановление.
21. Удалять кластер.

Система автоматически определяет зависимости между компонентами и правильный порядок установки (движок на основе DAG — графа задач). От пользователя никогда не требуется знать kubeadm, systemd, containerd, внутреннее устройство CNI, CoreDNS, kubelet, iptables/nftables, Helm, cert-manager, StorageClass, Prometheus, Grafana, Loki, OpenTelemetry, RBAC, etcd, cloud-init, Ansible, Terraform, детали SSH, TLS или PKI (промпт §2). Опытные пользователи могут открыть **Advanced configuration** (расширенную конфигурацию) и управлять всем.

## 4. Режимы

| Режим | Сценарий | Для кого |
|---|---|---|
| **Auto** (основной UX) | Имя, инфраструктура, окружение, размер, доступность → движок принятия решений формирует полный план с обоснованиями («Почему такая конфигурация?») → при желании ручные изменения → Deploy | Для всех; точка входа по умолчанию |
| **Simple** | Инфраструктура → пресет (Development, Staging, Production, High Availability, Minimal, Edge, GPU, AI/ML, Custom) → проверка → Deploy | Пользователи, которым нужен известный стандарт |
| **Advanced** | Мастер из 15 шагов (Basics … Deploy) + полное дерево конфигурации + YAML-редактор с синхронизацией UI ↔ YAML в обе стороны | DevOps/SRE |
| **Enterprise** | Каталог сервисов → золотой шаблон (golden template) → допустимые параметры → проверка политик и безопасности → стоимость → согласование → развёртывание → непрерывный контроль состояния, обнаружение дрейфа, резервное копирование, обновления, соответствие требованиям (compliance) | Организации |

Все режимы формируют одну и ту же декларативную **ClusterSpec** и используют один и тот же движок. При переключении режимов данные сохраняются.

## 5. Редакции

| | **Community** (Apache-2.0) | **Enterprise** (коммерческая, `ee/`) |
|---|---|---|
| Провижининг (provisioning) и жизненный цикл (все провайдеры, дистрибутивы, аддоны, Auto/Simple/Advanced, обновления, масштабирование, резервное копирование/восстановление, состояние (health), шаблоны, CLI, API, вебхуки, уведомления) | ✓ | ✓ |
| Организации / проекты | UI для одной организации (мультитенантная модель данных) | Много организаций, команды, квоты |
| Аутентификация | Локальные учётные записи, API-ключи | + SSO (OIDC, SAML), SCIM, политика MFA, сервисные аккаунты, управление сессиями |
| Авторизация | Встроенные роли | + пользовательские роли, ABAC |
| Корпоративное управление (governance) | Встроенные защитные ограничения (guardrails) | + движок политик (policy as code), согласования, запросы на изменение, золотые шаблоны, окна обслуживания |
| Аудит | Журнал аудита, экспорт в JSON/CSV | + экспорт в SIEM/syslog/S3, блокировка срока хранения (retention lock) |
| Соответствие требованиям и безопасность | Усиленные (hardened) профили | + центр соответствия требованиям (compliance center), оценка защищённости (security posture), безопасность образов, агрегация уязвимостей |
| Секреты | Конвертное шифрование (envelope encryption) с локальным ключом | + OpenBao/Vault, облачный KMS, BYOK |
| Парк кластеров (fleet) | Дашборд для нескольких кластеров | + группы кластеров, канареечные обновления парка, мультирегиональность |
| DR и офлайн | Резервное копирование/восстановление | + межрегиональное DR, RPO/RTO, бандлы для изолированных (air-gapped) установок |
| Платформа | Один экземпляр или простая HA | + эталонная HA-архитектура, SLO, управление затратами, бюджеты, инциденты, каталог сервисов, Terraform-провайдер |

Правило границы open-core: **Community — полноценный продукт для провижининга производственного уровня. Enterprise добавляет корпоративное управление, масштаб и интеграции. Она никогда не убирает и не урезает базовые возможности провижининга** (ADR-0002). Функции включаются и ограничиваются в одном месте (`EntitlementService`), а не разбросанными проверками `if enterprise` (промпт §218).

## 6. MVP

**MVP = фазы 1–4** ([ROADMAP](ROADMAP.ru.md)): *один клик от доступных по SSH хостов Ubuntu/Debian до готового к продакшену кластера kubeadm — наблюдаемого и с возможностью возобновления.*

Входит:
- локальная аутентификация + API-ключи, UI для одной организации/проекта на мультитенантной модели данных, журнал аудита
- хранилище учётных данных (SSH-ключи, ключи S3) с конвертным шифрованием
- провайдер bare metal / существующих хостов по SSH с проверкой ключа хоста и предварительными проверками (preflight)
- kubeadm: одиночный control plane и HA (3 узла control plane с kube-vip), containerd
- Cilium (по умолчанию), затем Calico и Flannel
- Gateway API: CRD под управлением платформы + Cilium Gateway (альтернатива — Envoy Gateway)
- MetalLB (или Cilium LB-IPAM)
- local-path, NFS CSI, Longhorn
- cert-manager с Let's Encrypt / внутренним CA / самоподписанными сертификатами
- metrics-server, kube-prometheus-stack + дашборды Grafana, Loki
- резервное копирование снимков etcd в S3-совместимое хранилище
- движок проверки состояния (health) и дашборд кластера
- прогресс в реальном времени с возобновлением, повтором и объяснимыми ошибками
- план / пробный прогон (dry run); шаблоны; пресеты режима Simple (Simple Mode); мастер режима Advanced (Advanced Mode); YAML ↔ UI
- скачивание kubeconfig; удаление кластера
- CLI (`create`, `plan`, `deploy --watch`, `list`, `get`, `kubeconfig`, `destroy`)
- установка через docker compose; CI со сканированием безопасности
- документация на английском и русском языках

Не входит в MVP: облачные провайдеры, k3s/RKE2, обновления Kubernetes и восстановление на базе Velero (фаза 6), движок принятия решений режима Auto (Auto Mode) (фаза 5; пресеты уже есть), GitOps, все функции Enterprise.

## 7. Не-цели

- Не «ещё один UI поверх kubeadm» и не запускатель shell-скриптов. Ценность — в движке, каталоге, правилах совместимости и объяснимости.
- Не универсальный инструмент «инфраструктура как код». Terraform/OpenTofu и Ansible не оборачиваются в ядре (ADR-0013).
- Не PaaS для рабочих нагрузок (нет конвейеров сборки и развёртывания приложений). Доставку рабочих нагрузок покрывает интеграция с GitOps.
- Никаких обещаний юридического соответствия требованиям. Платформа сообщает о мерах контроля и доказательствах, но никогда не утверждает, что организация «соответствует требованиям».
- Никаких выдуманных цен и SLA. Оценка стоимости появляется, только если провайдер публикует цены, а целевые показатели SLA — только при соответствующей инфраструктуре.

## 8. Метрики успеха

| Метрика | Цель (MVP) |
|---|---|
| Время от «хосты готовы» до production-кластера в статусе READY (6 узлов, стандартные аддоны) | ≤ 20 мин, без ручных шагов после Deploy |
| Доля успешных развёртываний на поддерживаемых ОС/оборудовании (E2E уровней Tier 2/3) | ≥ 98 % |
| Восстановление: прерванные развёртывания, которые возобновляются до READY без ручного вмешательства на узлах | ≥ 95 % |
| Ошибки, показанные с объяснением что/почему/где/как исправить | 100 % известных классов ошибок |
| Действия пользователя для создания кластера в режиме Auto | ≤ 6 полей ввода + Deploy |
| Безопасность | 0 секретов в логах/API (canary-тесты), 0 непринятых уязвимостей уровня high/critical на момент релиза |

## 9. Принципы, определяющие продукт (из спецификации)

- **Объяснять всё.** У рекомендаций есть обоснования, у сбоев — причины и способы исправления, планы показывают diff и необратимые шаги.
- **Никогда не создавать заведомо сломанный кластер.** Движок совместимости плюс каталог версий.
- **Никогда не выбирать рискованные настройки молча.** Предупреждения о безопасности с явным выбором.
- **Пробный прогон везде.** Сначала план, затем предпросмотр, затем применение.
- **Бэкенд — источник истины.** Закрытие браузера никогда не останавливает развёртывание и не приводит к его потере.
- **Всё по принципу API-first.** UI и CLI — клиенты одного и того же API.
- **Безопасность прежде всего.** Учётные данные — главная ценность (crown jewels): они зашифрованы, маскируются и все обращения к ним проходят аудит.
- **Production-мышление с первого дня.** Никаких фиктивных развёртываний, никаких захардкоженных секретов, IP-адресов или паролей вне изолированных тестовых фикстур.
