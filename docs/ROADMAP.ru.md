# Дорожная карта

> Статус: **Предложено** (Phase 0) — ожидает утверждения владельцем. Язык: [English](ROADMAP.md) · Русский
>
> Связанные документы: [PRODUCT](PRODUCT.ru.md) · [ARCHITECTURE](ARCHITECTURE.ru.md) · [DECISIONS](DECISIONS.ru.md)

В спецификации продукта две дорожные карты: фазы 0–10 в промпте §101–111 и обновлённый список в §238. Эта дорожная карта объединяет их, принимает порядок из §238 как определяющий и добавляет фазу 0 (исследование и архитектура). Правило упорядочивания — важнейшее требование спецификации к реализации (§239): **функции Enterprise не разрабатываются, пока базовый движок провижининга (provisioning) не доказал, что умеет надёжно доводить инфраструктуру до работоспособного кластера и восстанавливаться после сбоев.**

Каждая фаза проходит один и тот же цикл (промпт §122): сначала документация → код → тесты → линтинг → модульные тесты → интеграционные тесты → сборка → Docker → E2E, где возможно → исправления → обновление документации → краткий отчёт (в формате промпта §123). Каждая фаза завершается чем-то работающим (`make dev` работает, промпт §113) и **контрольной точкой фазы**: критерии завершения ниже, плюс [Definition of Done (критерии готовности)](#definition-of-done-критерии-готовности), плюс ревью модели угроз.

## Фаза 1 — Ядро / фундамент

**Цель:** работающий каркас, устроенный как продакшен-система. Настоящее хранение данных, аутентификация, тенантность, API, оболочка UI, CI. Кластеры можно создавать как записи, а «развёртывать» — только с помощью **симулированного провайдера** (явно предназначенного только для тестов: промпт §102 допускает здесь заглушку, §115 запрещает фиктивное развёртывание в продакшене, и симулированный провайдер удовлетворяет обоим требованиям).

**Состав работ:**
- Структура монорепозитория, Go-модуль, Makefile, golangci-lint, pnpm workspace, pre-commit (gofumpt, lint, gitleaks).
- Каркас API v1 на Huma (OpenAPI 3.1 хранится в репозитории, проверки oasdiff/vacuum, сгенерированные TS-типы, типизированный Go-клиент); ошибки в формате problem+json; каталог ошибок (en/ru).
- PostgreSQL 18 + миграции goose (идентификация, тенантность, RBAC, учётные данные/секреты, кластеры, ревизии спецификаций, операции, события, аудит, идемпотентность, outbox); RLS с первой миграции.
- AuthN: локальные пользователи (argon2id), сессии, CSRF, API-ключи. AuthZ: каталог разрешений, встроенные роли, привязки ролей, `Authorizer`.
- Организации и проекты (в UI — одна организация по умолчанию, под капотом — мультитенантность), CRUD кластеров с ClusterSpec v1alpha1 (строгий YAML/JSON, JSON Schema), ревизии спецификаций и diff.
- Хранилище учётных данных с конвертным шифрованием (envelope encryption, локальный KEK), API только на запись, маскирование секретов (redaction), канареечные тесты на утечки.
- Интеграция River, транзакционный outbox, журнал аудита (цепочка хешей), вебхуки (Standard Webhooks) с защитой от SSRF.
- Симулированный провайдер + минимальный путь движка (линейный список задач), чтобы полный цикл «развёртывания» работал от начала до конца; настоящий движок — в фазе 2.
- Веб: оболочка приложения, маршрутизация, тема (светлая/тёмная), i18n (en/ru), вход, список и карточка кластера, YAML-редактор (Monaco), учётные данные, настройки; сгенерированный API-клиент.
- Каркас CLI: `login`, `cluster create|list|get|delete`, `validate`.
- Docker: многоэтапные (multi-stage) образы, `make dev` (compose: postgres, api, worker, web), `.env.example`.
- CI: линтинг → модульные тесты → интеграционные тесты → сборка → сканирование безопасности (govulncheck, OSV/Grype, gitleaks, сканирование образов, SBOM) → E2E (Playwright на симулированном провайдере) → docker build.
- Документация: README, DEVELOPMENT.md, DEPLOYMENT.md (dev/self-hosted), CONTRIBUTING.md, SECURITY.md, API.md и руководства по добавлению провайдера, дистрибутива, аддона, CNI, провайдера хранилища, ingress/gateway и пресета (промпт §75).

**Критерии завершения:** в UI пользователь входит в систему, создаёт кластер из пресета/YAML, развёртывает его симулированным провайдером, видит прогресс, и запись в итоге переходит в READY. Записи аудита созданы. Тесты матрицы авторизации и выхода за пределы тенанта проходят. CI зелёный. `make dev` работает на чистом checkout.

## Фаза 2 — Движок провижининга

**Состав работ:** планировщик (planner: вклады плагинов в задачи, граф возможностей, топологическая сортировка, diff, флаги необратимости, оценки), диспетчер DAG (DAG scheduler) с ограничениями параллелизма, исполнитель с арендами (lease)/heartbeat/fencing, контракт задачи (`Check/Run/Rollback`), типизированные ошибки и политики повторов, circuit breaker, политики реакции на сбой (pause/rollback/abort), возобновление (Resume), повтор (Retry) задачи, отмена, откат обратимых задач, конечные автоматы кластера/операции/задачи, события операций через SSE (`Last-Event-ID`) с рассылкой через LISTEN/NOTIFY, поиск и скачивание структурированных логов, UI отчёта о сбое (что / почему / где / как исправить), эндпоинт и UI для плана / пробного прогона (dry run), ключи идемпотентности на всём пути запроса.

**Критерии завершения:** на симулированном провайдере со скриптами внедрения сбоев каждый сценарий сбоя из [стратегии тестирования, §5](architecture/testing-strategy.ru.md) даёт правильный отчёт и завершается восстановлением. Тест с принудительным завершением воркера (kill-the-worker) проходит 100 из 100 итераций с одинаковым итоговым состоянием. Браузер можно закрыть посреди развёртывания и открыть снова — отображение хода восстанавливается.

## Фаза 3 — Kubernetes на bare metal (первый реальный кластер)

**Состав работ:** подсистема SSH (ключи, пароль, агент, jump-хосты, прокси, проверка ключа хоста и UI подтверждения TOFU, пул соединений, таймауты), провайдер bare metal (объявленные хосты, обнаружение и сбор фактов), предварительные проверки (preflight) — ОС/CPU/RAM/диск/ядро/cgroup v2/swap/модули/sysctl/порты/DNS/задержка/синхронизация времени — с UI ✓/⚠/✗, слой bootstrap с `OSFamily` debian (Ubuntu 24.04, 26.04; Debian 13; Debian 12 — по возможности (best-effort)), подписанный node helper, containerd (версия закреплена в каталоге), kubeadm (v1beta4): один узел control plane + HA (3 узла control plane, stacked etcd, kube-vip как static pod с шагом bootstrap через super-admin.conf), join, reset, kubeconfig (привязанный к пользователю, короткоживущий), CRD Gateway API (под управлением платформы), Cilium (CNI по умолчанию), базовый движок проверки состояния (health), удаление кластера (reset узлов).

**Критерии завершения:** E2E уровня Tier 2 (контейнерные узлы) создаёт кластер с одним узлом control plane и с тремя — по настоящему SSH. `kubectl get nodes` и `get pods -A` показывают исправное состояние. Повторный запуск операции ничего не меняет (no-op). Тесты сбоев, помеченные ★, проходят на Tier 2. Tier 3 (реальные ВМ) запускается, если доступен аккаунт; иначе в отчёте этот пробел указывается явно.

## Фаза 4 — Кластер для продакшена

**Состав работ:** контроллер Gateway (по умолчанию Cilium Gateway; альтернатива — Envoy Gateway), MetalLB (L2/BGP) и вариант с Cilium LB-IPAM, хранилище (local-path, NFS CSI, Longhorn), cert-manager (+ издатели, issuers: Let's Encrypt HTTP-01/DNS-01, внутренний CA, самоподписанные, существующие), metrics-server, пресеты наблюдаемости (Basic / Standard / Full: kube-prometheus-stack, Grafana с дашбордами и передачей учётных данных, Loki + Alloy, опционально Tempo/OpenTelemetry), резервное копирование снимков etcd в S3-совместимое хранилище, движок проверки состояния (все проверки), Calico и Flannel — после стабилизации Cilium, режим Simple (Simple Mode, пресеты), шаблоны (сохранение/повторное использование/версии), мастер режима Advanced (15 шагов) с формами, учитывающими зависимости, дашборд кластера, представление узлов (cordon/drain/uncordon), управление аддонами (установка/удаление), уведомления (в приложении, email, вебхук, Slack, Telegram), CLI deploy/watch/kubeconfig, глобальный поиск, палитра команд.

**Критерии завершения (= контрольная точка MVP):** основной сценарий из промпта §120 (с bare metal вместо Hetzner) проходит от начала до конца из UI и из CLI: Production HA, Cilium, Gateway, MetalLB, Longhorn, Prometheus + Grafana, Loki, cert-manager, резервное копирование etcd в S3-совместимое хранилище (в тестах — SeaweedFS или Ceph RGW), затем READY с URL Grafana и kubeconfig. Все тесты сбоев проходят. Проведено ревью безопасности MVP. Документация полная на en/ru.

## Фаза 5 — Режим Auto (Auto Mode)

**Состав работ:** движок принятия решений (правила, обоснования, альтернативы, закрепления (pins), предупреждения о рисках), UI «Почему такая конфигурация?», переопределения с пересчётом, пресеты как входные данные движка, движок совместимости, выведенный в UI (скрытие/блокировка вариантов с указанием причин), оценка стоимости там, где провайдеры публикуют цены (иначе — «недоступно»), оценки времени по истории, «Deploy» в один клик из формы из 5 вопросов (промпт §234), golden-file- и property-тесты.

**Критерии завершения:** Production + bare metal + Medium + HA → Deploy работает без дополнительного ввода, кроме учётных данных и хостов. Каждая рекомендация проходит проверку совместимости без единого результата уровня BLOCK (проверено property-тестами).

## Фаза 6 — Жизненный цикл

**Состав работ:** советник по обновлениям (upgrade advisor: оценка готовности, блокеры, поиск устаревших API, защита etcd) и оркестрированные обновления Kubernetes (узлы control plane по одному со снимками etcd, затем аддоны, затем рабочие узлы пакетами с drain), масштабирование (добавление/удаление рабочих узлов, пулы), резервное копирование/восстановление (Velero со снимками CSI/data mover + etcd), замена узлов, ротация сертификатов и учётных данных, импорт существующих кластеров через kubeadm/kubeconfig (обнаружение CNI, gateway/ingress, включая ingress-nginx с помощником миграции, хранилища, аддонов), обнаружение дрейфа (желаемое vs фактическое состояние) с реакцией только в виде оповещений.

**Критерии завершения:** на Tier 2 и Tier 3 проходит E2E обновления 1.36→1.37. Проходит масштабирование с 3 до 6 рабочих узлов. Цепочка backup → destroy → restore восстанавливает рабочие нагрузки и PV. Импорт кластера kind/k3d показывает корректную инвентаризацию.

## Фаза 7 — Несколько провайдеров

**Состав работ:** провайдер Hetzner Cloud (серверы, сети, файрволы, placement groups, LB для API-эндпоинта и Services, hcloud CCM + CSI, цены), затем AWS, GCP и Azure — по одному. Нативные SDK или бэкенд на Cluster API — решается по ADR-0013 в начале фазы. Дистрибутивы k3s и RKE2. Семейство ОС rhel (Rocky/Alma 9/10, SELinux в режиме enforcing).

**Критерии завершения:** каждый провайдер проходит набор контрактных тестов провайдера и обязательные E2E на своём реальном API (еженощно) с ограничением затрат. Режим Auto использует возможности и цены провайдеров.

## Фаза 8 — GitOps

**Состав работ:** аддоны Argo CD и Flux с автоматической регистрацией кластеров (промпт §27). Спецификации кластеров, хранящиеся в Git («кластер под управлением GitOps»: изменения из UI создают коммиты/PR или блокируются, промпт §200). Управление дрейфом с Git в качестве источника истины. Учётные данные Git — в хранилище учётных данных.

## Фаза 9 — Фундамент Enterprise (ee)

**Состав работ:** каталог `ee/` с коммерческой лицензией и build-тегом; EntitlementService с подписанными лицензиями; администрирование нескольких организаций; команды; пользовательские роли; условия ABAC; SSO (OIDC, SAML 2.0) через абстракцию IdentityProvider (Okta, Entra ID, Google Workspace, Keycloak, Auth0, универсальный провайдер); провижининг/депровижининг SCIM 2.0 с отзывом сессий и API-ключей; MFA (TOTP, WebAuthn) и политика MFA; сервисные аккаунты; управление сессиями (список устройств, отзыв всех сессий, обнаружение подозрительных сессий); поиск и экспорт аудита для Enterprise.

## Фаза 10 — Корпоративное управление (ee)

**Состав работ:** движок политик (политики как код, уровни INFO/WARNING/BLOCK, области действия и наследование global → org → project → environment → cluster с режимами inherit/override/restrict, адаптер OPA/Rego или Cedar), политики согласования, запросы на изменение (diff, риск, результаты проверки политик, согласующие), согласование развёртываний, окна обслуживания, золотые шаблоны (заблокированные поля, версии, наследование), центр соответствия требованиям (стандарты как сопоставления контролей, свидетельства; платформа никогда не заявляет о соответствии), состояние безопасности (security posture) каждого кластера (CIS через kube-bench/Kubescape).

## Фаза 11 — Парк кластеров Enterprise (ee)

**Состав работ:** группы кластеров; операции над парком (обновление 100+ кластеров пакетами с канареечным этапом, контрольными проверками состояния (health gates) и автоматической остановкой при превышении доли сбоев); мультирегиональность и размещение с учётом топологии (регионы, зоны, стойки, домены отказа); глобальный дашборд (состояние, развёртывания, резервные копии, безопасность, соответствие требованиям); политики жизненного цикла узлов (замена узлов старше N дней).

## Фаза 12 — Безопасность Enterprise (ee)

**Состав работ:** OpenBao/Vault (Transit KEK + бэкенд KV), AWS/GCP/Azure KMS, BYOK, инструменты ротации ключей; безопасность образов (разрешённые/запрещённые реестры, проверка подписей через Sigstore/Kyverno, приватный реестр по умолчанию, интеграция с Harbor); управление уязвимостями (агрегация данных Trivy Operator); проверка цепочки поставок для артефактов каталога; подписанные релизы с SBOM и provenance (уже есть в CI с фазы 1, теперь проверяются принудительно при установке/импорте).

## Фаза 13 — DR и air-gap в Enterprise (ee)

**Состав работ:** межрегиональное резервное копирование и репликация, DR-процессы (runbook-и переключения (failover) и восстановления, выполняемые как операции), отслеживание и отображение RPO/RTO, политики резервного копирования по окружениям, резервное копирование и восстановление самой платформы; изолированная (air-gapped) установка: `farvater bundle create|verify|import`, приватный OCI-реестр, офлайн Helm-чарты, офлайн-пакеты и бинарники Kubernetes и ОС.

## Фаза 14 — Платформа Enterprise (ee)

**Состав работ:** эталонная HA-архитектура платформы (api×3, worker×3, PostgreSQL HA), дашборды SLO (доступность API, успешность развёртываний, успешность резервного копирования), управление затратами (распределение по организации/проекту/команде/окружению/центру затрат), бюджеты с порогами и действиями по политикам, квоты (кластеры, узлы, CPU, RAM, хранилище, развёртывания на область действия), управление инцидентами (автоматическое создание инцидентов, назначение, хронология, постмортемы; PagerDuty/Opsgenie/Slack/Teams), каталог сервисов (шаблоны, наборы аддонов, профили безопасности и наблюдаемости), самообслуживание в рамках политик, провайдер Terraform/OpenTofu (поверх публичного API), корпоративные интеграции (Jira, ServiceNow, SIEM).

## Definition of Done (критерии готовности)

Функция считается готовой, только если (промпт §125, а для Enterprise — также §237):
- она реализована, и её точки интеграции работают;
- ошибки обрабатываются, а ошибки, которые видит пользователь, объяснимы (что / почему / где / как исправить);
- есть тесты на нужных уровнях (см. [стратегию тестирования](architecture/testing-strategy.ru.md)); линтер, проверки типов и сборка проходят; основной успешный сценарий (happy path) работает;
- документация обновлена на английском и русском;
- нет очевидных проблем безопасности, захардкоженных секретов и необъяснённых TODO;
- для функций Enterprise дополнительно: API + UI + разрешения + аудит + миграция, если нужна + наблюдаемость + обработка сбоев + E2E + поддержка в CLI/API, где применимо + проверенная изоляция тенантов + редакция Standard не сломана.

## Главные риски для плана

Полный список с мерами снижения — в [ARCHITECTURE, раздел «Риски»](ARCHITECTURE.ru.md). Сильнее всего на сроки влияют:
1. Объём работ очень велик по сравнению с возможностями команды. Меры снижения: строгие контрольные точки фаз и фокус на MVP.
2. Нет реального оборудования для тестирования. Меры снижения: контейнерные узлы Tier 2 с фазы 3 и небольшой облачный бюджет на Tier 3, прежде чем считать MVP завершённым.
3. Быстрые изменения экосистемы (три минорных релиза Kubernetes в год; изменения в Gateway API, containerd, etcd). Мера снижения: подписанный каталог на основе данных с автоматическими PR обновлений.
