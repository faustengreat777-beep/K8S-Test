# ADR-0025: Аутентификация — серверные сессии для UI, хешированные API-ключи для автоматизации, SSO в Enterprise

- Статус: Предложено
- Дата: 2026-10-06
- Язык: [English](0025-authentication-sessions-and-api-keys.md) · Русский

## Контекст

Спецификация перечисляет `JWT_SECRET` среди переменных окружения (промпт §84) и требует аутентификации для UI, API и CLI, истечения срока сессий, их обновления (refresh) и отзыва, списка сессий, а также MFA и SSO в Enterprise (промпт §142–146). API-ключи должны иметь ограниченную область действия (scope) и срок действия, поддерживать отзыв, показываться один раз и храниться в хешированном виде (промпт §146).

## Решение

- **Браузер**: непрозрачные (opaque) случайные токены сессий в cookie с префиксом `__Host-` (`HttpOnly; Secure; SameSite=Lax`). На сервере хранится только SHA-256 токена; сессия истекает по неактивности и по абсолютному сроку, токен ротируется при входе и при изменении привилегий, у каждого пользователя есть список сессий, можно отозвать одну сессию или все сразу. Защита от CSRF построена на синхронизирующем токене (synchronizer token).
- **API-ключи**: `fvt_<public id>_<secret>`. Префикс используется для поиска, а секрет проверяется через HMAC-SHA256 с серверным «перцем» (pepper). Ключи имеют ограниченную область действия (подмножество прав владельца) и срок действия, могут быть отозваны, фиксируют IP-адрес и время последнего использования и показываются один раз.
- **Никаких JWT для собственных (first-party) сессий.** Отзыв должен быть мгновенным, а сессии — доступными для просмотра списком; с состоянием на сервере это проще и безопаснее. JWT могут появляться только там, где их требует протокол: ID-токены OIDC от IdP и короткоживущие токены для будущего OAuth device flow.
- **Пароли**: argon2id с версионируемыми параметрами, проверка по базам утёкших паролей, нарастающая задержка между попытками входа и блокировка.
- **Enterprise**: OIDC и SAML 2.0 через абстракцию `IdentityProvider`; провижининг SCIM 2.0 с немедленным отзывом сессий и ключей при деактивации пользователя (deprovisioning); MFA (TOTP, WebAuthn/passkeys) с политикой на уровне организации; сервисные аккаунты.

## Рассмотренные альтернативы

- **Stateless JWT-сессии**: для отзыва нужны deny-листы (что возвращает состояние), ключи подписи становятся особо ценным секретом, а последствия кражи токена сложнее локализовать.
- **Только внешний прокси аутентификации (oauth2-proxy)**: недостаточно для API-ключей, CLI и детальной авторизации; тем не менее полезен как *опциональный* вариант развёртывания перед UI.

## Последствия

- Плюсы: мгновенный отзыв, простая ментальная модель, меньше секретов (`JWT_SECRET` не нужен; вместо него используются `SESSION_SECRET_FILE` и `API_KEY_PEPPER_FILE`).
- Минусы: поиск сессии при каждом запросе. Это дёшево благодаря индексу и небольшому кешу с коротким TTL на каждой реплике, а об отзыве реплики оповещаются через `NOTIFY`.
