# ADR-0008: Собственный DAG-движок провижининга; одно задание с арендой (lease) на операцию; Temporal пока не используется

- Статус: Предложено
- Дата: 2026-10-06
- Язык: [English](0008-provisioning-engine-execution-model.md) · Русский

## Контекст

Движок развёртывания — самый важный компонент (промпт §10). Развёртывания должны раскладываться на задачи с зависимостями (DAG, промпт §11). Они должны быть идемпотентными и возобновляемыми после прерывания (промпт §12), поддерживать откат там, где это безопасно (промпт §13), подчиняться управляемому конечному автомату (промпт §14), передавать прогресс в реальном времени (промпт §15) и выполняться вне HTTP-запросов (промпт §41). Спецификация называет Redis+BullMQ, RabbitMQ, NATS и Temporal кандидатами на роль очереди и просит обоснованного выбора.

## Решение

- Создать **собственный движок провижининга** в `internal/engine`:
  - **планировщик** (planner) превращает ResolvedSpec + наблюдаемое состояние в DAG задач, которые поставляют плагины (провайдер, слой bootstrap, дистрибутив, аддоны через зависимости по возможностям (capabilities));
  - **исполнитель** (executor) выполняет DAG с ограниченным параллелизмом (глобально / на кластер / на узел), типизированными ошибками, политиками повторов, тайм-аутами и автоматическими выключателями (circuit breakers);
  - **контракт задачи** `Check / Run / Rollback` с обязательной идемпотентностью;
  - **сначала сохранение (persistence-first)**: каждый переход задачи записывается в PostgreSQL до и после выполнения; для SSE дописываются события.
- **Единица выполнения = одно задание River на операцию** (ADR-0007), защищённое **арендой выполнения** (execution lease) с heartbeat, истечением срока и fencing при каждой записи. Аренда упавшего воркера истекает, и другой воркер возобновляет работу с сохранённых состояний задач.
- Политика обработки сбоев по умолчанию — **пауза** (с объяснением и доступными пользователю действиями). Автоматический откат выполняется только для обратимых задач.
- Ядро движка ничего не знает о конкретных провайдерах, дистрибутивах или аддонах.
- Подробности: [Движок провижининга](../provisioning-engine.ru.md).

## Рассмотренные альтернативы

| Вариант | Оценка |
|---|---|
| **Temporal** (durable workflows) | Высокая надёжность (durability) и повторы. Но он добавляет отдельно эксплуатируемый кластер (сервисы frontend/history/matching + собственная БД, опционально Elasticsearch). Это тяжело для self-hosted и изолированных (air-gapped) установок. Требования к детерминированности workflow усложняют динамические DAG, построенные из данных, а версионирование кода workflow между релизами нетривиально. Наши потребности (DAG, аренды, возобновление, события) с запасом покрываются PostgreSQL. **Пересмотреть**, если понадобится межрегиональная надёжная оркестрация в масштабе парка (Phase 11+); интерфейсы движка позволят заменить текущий исполнитель исполнителем на базе Temporal. |
| Одно задание в очереди на каждую задачу (fan-out в очереди) | Простые повторы для отдельных задач, но глобальные лимиты параллелизма, политика обработки сбоев и порядок выполнения требуют координации между заданиями, из-за чего поведение системы сложнее анализировать, а саму операцию сложнее приостанавливать и возобновлять как единое целое. |
| Argo Workflows / Tekton в управляющем кластере | Нужен управляющий кластер Kubernetes ещё до появления первого кластера (проблема курицы и яйца для bare metal); определения workflow на YAML противоречат нашим типизированным задачам. |
| Плейбуки Ansible в качестве движка | Слабая типизация и классификация ошибок, нет полноценной поддержки возобновления и состояния DAG, зависимость от среды выполнения Python, поверхность для инъекций через шаблонизированный YAML. |

## Последствия

- Плюсы: полный контроль над семантикой (пауза/возобновление, необратимые шаги, объяснимые сбои), для эксплуатации нужен только PostgreSQL, тестируемость с помощью симулированного провайдера и детерминированного планирования.
- Минусы: вся сложность движка workflow (аренды, fencing, восстановление) ложится на нас. Это смягчается небольшим хорошо протестированным ядром, хаос-тестами (kill-the-worker) и сохранением универсальности движка.
