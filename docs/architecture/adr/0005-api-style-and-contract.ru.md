# ADR-0005: REST/JSON API с контрактом OpenAPI 3.1 в репозитории (Huma, contract-first на Go), асинхронные операции и ошибки problem+json

- Статус: Предложено
- Дата: 2026-10-06
- Язык: [English](0005-api-style-and-contract.md) · Русский

## Контекст

UI, CLI, будущий провайдер Terraform/OpenTofu и автоматизация на стороне клиентов должны работать через один и тот же API, а в клиентах не должно быть бизнес-логики (промпт §40, §56, §57, §198). API нужны аутентификация, авторизация, валидация, пагинация, фильтрация, сортировка, идемпотентность, асинхронные задания, вебхуки, аудит и версионирование (промпт §40, §87). Развёртывания длятся долго и не должны выполняться внутри HTTP-запросов (промпт §41).

## Решение

- **REST поверх HTTPS с JSON**, ресурсно-ориентированные пути под `/api/v1`. В пределах v1 допускаются только аддитивные изменения. Ломающие изменения уходят в `/api/v2`, который обслуживается параллельно с v1, с заголовками `Deprecation`/`Sunset`.
- **Контракт OpenAPI 3.1 описывается типизированным кодом на Go с помощью Huma v2** (поверх роутера chi): операции объявляются структурами запросов и ответов с тегами валидации. Huma генерирует документ OpenAPI 3.1, JSON Schema, валидацию запросов и ошибки по RFC 9457.
- Сгенерированный документ `api/openapi/openapi.yaml` **хранится в репозитории** и считается контрактом:
  - в каждом PR виден его diff, поэтому изменения API проходят ревью так же, как код;
  - **oasdiff** блокирует ломающие изменения в пределах v1;
  - **vacuum** проверяет стиль и согласованность (линтинг);
  - задача CI завершается ошибкой, если закоммиченная спецификация или сгенерированные клиенты устарели.
- **Клиенты**: типы TypeScript генерируются из закоммиченной спецификации (`openapi-typescript` + `openapi-fetch`). CLI использует `pkg/client` — тонкий типизированный клиент поверх общих типов запросов и ответов. Внешние потребители (например, провайдер Terraform) могут генерировать клиенты по спецификации (oapi-codegen в режиме клиента).
- Каждый ответ в интеграционных тестах проверяется на соответствие закоммиченной спецификации (валидатором kin-openapi или libopenapi).
- **Длительная работа возвращает `202 Accepted` + ресурс `Operation`**. Прогресс считывается опросом (polling) или через SSE (ADR-0009).
- **Ошибки**: RFC 9457 `application/problem+json` со стабильным `code`, локализованными `title`/`detail`, `requestId`, ошибками полей `errors[]`, а для сбоев операций — ещё и с `location`, `remediation[]` и `actions[]`.
- Заголовок **Idempotency-Key** у POST-запросов, которые что-либо создают или запускают (окно повторного воспроизведения ответа — 24 ч). `ETag`/`If-Match` — для оптимистичной блокировки.
- **Курсорная пагинация**, явные параметры фильтрации и `orderBy` только по списку разрешённых полей.
- **Вебхуки** в формате Standard Webhooks (подписи HMAC-SHA256).
- Подробности: [Проектирование API](../api-design.ru.md).

## Рассмотренные альтернативы

| Вариант | Почему нет |
|---|---|
| gRPC (+ grpc-gateway) | Отлично подходит для взаимодействия между сервисами, но браузерам всё равно нужен шлюз; REST + OpenAPI удобнее для CLI, Terraform, curl и сторонних разработчиков |
| GraphQL | Гибкое чтение, но сложные авторизация на уровне полей, кеширование и ограничение частоты запросов; для длительных операций и SSE всё равно нужны REST-подобные эндпоинты |
| Spec-first с генерацией серверного кода (oapi-codegen, ogen) | Самый «чистый» подход contract-first, но на октябрь 2026 года генераторы для Go поддерживают OpenAPI 3.1 лишь частично: oapi-codegen называет свою поддержку 3.1 «начальной» (v2.8.0, июль 2026), а ogen требует препроцессоров для nullability в 3.1. Нам пришлось бы либо остаться на 3.0, либо бороться с генератором. Huma нативно выдаёт корректную спецификацию 3.1, а хранение сгенерированной спецификации в репозитории вместе с блокировкой ломающих изменений гарантирует, что контракт проходит ревью до слияния. Пересмотреть, когда серверная генерация для 3.1 станет зрелой |
| Написанные вручную обработчики + написанная вручную спецификация | Расхождение кода и спецификации неизбежно |
| Aggregated API в стиле Kubernetes / CRD в качестве API продукта | Элегантно для инструментов, работающих внутри кластера, но сама платформа не является контроллером Kubernetes и должна работать без управляющего кластера (management cluster) |

## Последствия

- Плюсы: единый контракт для всех клиентов, сгенерированный код вместо написанных вручную DTO, изменения API проходят ревью, ошибки единообразны.
- Минусы: контракт живёт в типах Go, поэтому участники, не пишущие на Go, просматривают diff сгенерированного YAML, а не редактируют спецификацию напрямую. Huma — проект, который ведёт в основном один мейнтейнер (MIT, v2 стабильна с 2023 года); этот риск смягчается тем, что закоммиченная спецификация переносима на другие генераторы.
