# ADR-0003: Модульный монолит с одним серверным бинарником и ролями процессов

- Статус: Предложено
- Дата: 2026-10-06
- Язык: [English](0003-modular-monolith.md) · Русский

## Контекст

Платформе нужны API, фоновые воркеры для длительного провижининга, веб-интерфейс, CLI, миграции базы данных, а позже — модули Enterprise. Спецификация требует надёжности продакшен-уровня, простого локального процесса разработки (`make dev`), самостоятельной (self-hosted) и изолированной (air-gapped) установки, а также варианта с высокой доступностью (HA) для Enterprise (промпт §43, §77, §179–182). Команда небольшая. Предметная область тесно связана транзакционно: создание операции должно атомарно записать состояние кластера, задачи, аудит, события outbox и задание.

## Решение

- Строим **модульный монолит на Go**: один репозиторий, один Go-модуль, один **серверный бинарник** с ролями процессов, которые выбираются подкомандой: `api`, `worker`, `all`, `migrate`, `admin`, `version`. CLI — отдельный небольшой бинарник.
- Границы модулей — явные пакеты в `internal/` (domain, app, engine, api, authn, authz, secrets, catalog, compat, recommend, health, audit, …) с правилами импорта, которые проверяются в CI (см. ADR-0004).
- Роли используют общий код, но различаются привилегиями. Только `worker` может расшифровывать учётные данные и обращаться к инфраструктуре клиента. `api` не может этого никогда (граница доверия, см. модель безопасности).
- Горизонтальное масштабирование — запуском дополнительных реплик `api` и `worker`. Их работу координирует PostgreSQL (ADR-0007, ADR-0008).

## Рассмотренные альтернативы

| Вариант | Почему нет (сейчас) |
|---|---|
| Микросервисы (отдельные сервисы API, движка, уведомлений, аудита) | Распределённые транзакции или саги для каждого изменения состояния, больше инфраструктуры (service mesh, шина сообщений), сложнее самостоятельная установка и air-gap, нет явного выигрыша в масштабировании при нашем размере |
| Один процесс без ролей | Нельзя отделить уровень, хранящий учётные данные, от уровня, доступного из интернета; нельзя масштабировать воркеры независимо |
| Бессерверные функции (serverless) | Не подходят из-за длительных операций SSH/Helm, air-gap и самостоятельной установки |

## Последствия

- Плюсы: простое развёртывание (один бинарник или образ), ACID-транзакции между модулями, удобная локальная разработка, небольшой объём поставки для air-gap, меньше движущихся частей, которые нужно защищать.
- Плюсы: позже модуль можно выделить в отдельный сервис, потому что его граница уже оформлена как интерфейс.
- Минусы: риск размывания границ модулей. Он снижается правилами импорта в CI и код-ревью.
- Минусы: единый цикл релизов для всех модулей. На текущем этапе это приемлемо.
