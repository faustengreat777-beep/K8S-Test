# ADR-0004: Идиоматичная для Go структура монорепозитория с одним Go-модулем

- Статус: Предложено
- Дата: 2026-10-06
- Язык: [English](0004-repository-layout.md) · Русский

## Контекст

Спецификация предлагает структуру в стиле TypeScript (`apps/`, `packages/`, а также `providers/`, `distributions/`, `addons/` на верхнем уровне) и прямо допускает более правильную структуру, если такая найдётся (промпт §76). Бэкенд написан на Go, фронтенд — на TypeScript, и оба находятся в одном репозитории. Границы плагинов (провайдеры, дистрибутивы, аддоны) должны быть достаточно чистыми, чтобы новые реализации не требовали переписывать ядро (промпт §114).

## Решение

- Структура: `cmd/` (бинарники), `internal/` (приватный код, изоляцию обеспечивает компилятор), `pkg/` (небольшой публичный API: `sdk`, `spec`, `client`), `plugins/` (провайдеры, дистрибутивы, семейства ОС, аддоны), `catalog/` (данные), `api/openapi/`, `migrations/`, `web/` (pnpm workspace), `ee/` (Enterprise, позже), `deploy/`, `test/`, `hack/`, `docs/`. Полное дерево: [структура репозитория](../repository-structure.ru.md).
- **Один Go-модуль** в корне репозитория. `pkg/sdk` может стать отдельным модулем, когда третьи стороны начнут собирать на его основе плагины.
- Правила зависимостей (domain → ничего; engine → domain + sdk; plugins → только sdk; ядро никогда не импортирует `ee/`) проверяются в CI с помощью `depguard`/линтинга границ импорта.
- Код Enterprise находится в `ee/` в том же репозитории, под отдельной лицензией и тегом сборки `ee` (ADR-0002).
- Путь Go-модуля: `github.com/faustengreat777-beep/k8s-test` до тех пор, пока репозиторий не переименован по названию продукта. Переименовать его рекомендуется до Фазы 1, пока это ещё дёшево.

## Рассмотренные альтернативы

- **`apps/` + `packages/`, как предложено**: идиоматично для монорепозиториев на Node, но в Go теряется инкапсуляция через `internal/` и появляется множество крошечных модулей.
- **Многомодульный Go workspace (по модулю на плагин)**: независимое версионирование, но тяжёлое управление релизами, директивы `replace` и более медленная сборка. Пока преждевременно.
- **Отдельные репозитории для веба, CLI и плагинов**: изменения, затрагивающие несколько репозиториев, становятся медленными, а API и сгенерированный код расходятся.

## Последствия

- Плюсы: инкапсуляция, которую обеспечивает компилятор, чёткая публичная поверхность, один `go build`, атомарные сквозные изменения.
- Минусы: у фронтенда и бэкенда общие CI и цикл релизов. Это приемлемо и даже желательно, поскольку UI — клиент той же версии API.
