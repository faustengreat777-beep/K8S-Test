# ADR-0027: Моделировать «Deployment» из спецификации как Operation / OperationTask

- Статус: Предложено
- Дата: 2026-10-06
- Язык: [English](0027-operation-instead-of-deployment.md) · Русский

## Контекст

Спецификация называет длительную единицу изменений `Deployment`, а её шаги — `DeploymentTask` (промпт §11, §58). Тот же механизм нужен и для обновлений (upgrade), масштабирования, изменений аддонов, резервного копирования, восстановления, ротаций, замены узлов, импорта и удаления (destroy) (промпт §29). В продукте для Kubernetes слово «Deployment» означает ещё и ресурс `apps/v1 Deployment`, что порождает неоднозначность в коде, API и логах.

## Решение

- В коде, базе данных и API единицей является **`Operation`** с полем `type` (`create`, `apply`, `upgrade`, `scale`, `addon-install`, `addon-remove`, `backup`, `restore`, `rotate-certificates`, `rotate-credentials`, `node-replace`, `import`, `destroy`, `preflight`), а её шаги — **`OperationTask`**.
- Тексты в UI написаны естественным языком: «Развёртывание…», «Идёт развёртывание», «Обновление…».
- Имена событий вебхуков из спецификации сохранены для совместимости: `deployment.started|completed|failed` (отправляются для операций тех типов, которые изменяют инфраструктуру кластера). Имена разрешений используют `deployment:*`, как в спецификации (промпт §138).

## Рассмотренные альтернативы

- **Оставить `Deployment` везде**: неоднозначно рядом с `Deployment` из Kubernetes и вводит в заблуждение для удаления, резервного копирования и восстановления.
- **`Run` / `Job`**: `Job` конфликтует с Kubernetes и заданиями River, а `Run` слишком расплывчато.

## Последствия

- Плюсы: однозначные код и API. Один механизм охватывает все действия жизненного цикла (похожая концепция — «long-running operations» в Google AIP-151).
- Минусы: необходимо задокументировать соответствие формулировкам спецификации. Это соответствие фиксируют данный ADR и модель данных.
