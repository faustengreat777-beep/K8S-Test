# ADR-0009: Server-Sent Events для отображения прогресса в реальном времени на основе журнала событий с возможностью воспроизведения

- Статус: Предложено
- Дата: 2026-10-06
- Язык: [English](0009-real-time-updates-sse.md) · Русский

## Контекст

UI должен показывать прогресс развёртывания и живые логи в реальном времени (промпт §15) через WebSocket или SSE (промпт §42). Закрытие браузера не должно приводить к потере данных, а при возвращении UI восстанавливает состояние с бэкенда (промпт §66). Реплик API может быть несколько.

## Решение

- Использовать **Server-Sent Events** (`text/event-stream`) для прогресса операций (`/operations/{id}/events`) и дашбордов (`/events?clusterId=`).
- Каждое событие — это строка в `operation_events` с монотонно возрастающим `id`. Поле SSE `id:` равно идентификатору этой строки. При переподключении клиент отправляет `Last-Event-ID` (нативный `EventSource` делает это автоматически), а сервер воспроизводит события из БД и затем продолжает передавать новые в реальном времени.
- Рассылка между репликами (fan-out): воркеры выполняют `NOTIFY` после фиксации событий. Каждая реплика API выполняет `LISTEN` и отправляет новые строки своим подписчикам. Ни Redis, ни брокер сообщений не нужны.
- Комментарии-heartbeat каждые 15 с; `retry: 3000`; `event: end` при терминальных состояниях; ограничение числа соединений на пользователя.
- WebSocket зарезервирован для будущего интерактивного терминала узла/пода, где нужен двунаправленный обмен.

## Рассмотренные альтернативы

| Вариант | Почему нет |
|---|---|
| WebSocket | Двунаправленный, а для прогресса это не нужно. Собственный протокол переподключения и возобновления всё равно пришлось бы делать, а через некоторые прокси он проходит хуже. Нет встроенной семантики возобновления |
| Long polling | Работает везде, но увеличивает задержку и нагрузку на сервер. Сохранён как запасной вариант: `GET /operations/{id}/events?after=` без SSE |
| Стриминг gRPC | Браузерам нужен прокси (grpc-web), что добавляет сложности |

## Последствия

- Плюсы: просто и нативно для HTTP (работает с cookie-сессией и с CLI). Встроенное возобновление через `Last-Event-ID`. Журнал в БД бесплатно даёт историю, поиск и аудит.
- Минусы: передача только в одну сторону. Для долгоживущих соединений нужно настраивать тайм-ауты прокси, и в этом помогают heartbeat-сообщения. Каждый открытый поток занимает горутину и долю подписки LISTEN, поэтому действуют ограничения на пользователя.
