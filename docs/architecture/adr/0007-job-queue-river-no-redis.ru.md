# ADR-0007: Очередь заданий River (на базе PostgreSQL); PostgreSQL для pub/sub и блокировок; Redis не требуется

- Статус: Предложено
- Дата: 2026-10-06
- Язык: [English](0007-job-queue-river-no-redis.md) · Русский

## Контекст

Развёртывания должны выполняться асинхронно: API → очередь заданий → воркер → движок развёртывания (промпт §41). Спецификация называет варианты Redis + BullMQ, RabbitMQ, NATS и Temporal и просит обоснованного выбора. Кроме того, среди настроек в ней указан `REDIS_URL` (промпт §84). Исследование (2026-10-06):
- **River v0.49** (ядро под MPL-2.0, версия до 1.0) предлагает транзакционную постановку в очередь, уникальные задания, повторы с нарастающей задержкой (backoff), отложенные и периодические задания, приоритеты, несколько очередей и выбор лидера. Его *workflows*, пакетная обработка (batching) и лимиты параллелизма есть только в коммерческой River Pro, которая нам не нужна.
- **asynq** требует Redis и не умеет ставить задания в очередь в одной транзакции с PostgreSQL.
- **Temporal** (MIT) требует кластера из нескольких сервисов, а также обновлений схемы.
- **NATS** остаётся под Apache-2.0 в рамках Linux Foundation.
- **Redis 8** распространяется под тремя лицензиями: RSAL/SSPL/**AGPL**.
- **Valkey 9.1** — под BSD-3 (Linux Foundation).
- **BullMQ** — библиотека для Node.js.

## Решение

- **Очередь заданий: River** с драйвером pgx v5. Задания вставляются **в той же транзакции**, что и доменные изменения, которым они нужны, поэтому потерянных или фантомных заданий не бывает. Применение: `operation.run` (уникальное для каждой операции, ADR-0008), периодический опрос состояния (health), доставка вебхуков и уведомлений, очистка по сроку хранения (retention) и обслуживание, синхронизация каталога.
- DAG мы реализуем сами (ADR-0008) и **не зависим от возможностей River Pro**. River используется без изменений (пофайловый копилефт MPL-2.0 соблюдается за счёт использования без модификаций и учитывается в NOTICE). Версия River закреплена из-за ломающих изменений до версии 1.0, а обновления тестируются.
- **Pub/sub**: PostgreSQL `LISTEN/NOTIFY` (рассылка (fan-out) SSE, сигналы отмены, широковещательное оповещение об отзыве сессий).
- **Блокировки и координация**: advisory-блокировки PostgreSQL (миграции, цепочка аудита для каждой организации) и строки аренды (lease) с fencing (операции).
- **Redis не требуется**: `REDIS_URL` из спецификации исключён. **Valkey** (BSD-3) — *необязательный* бэкенд для общего ограничения частоты запросов (rate limiting) и кеширования в очень крупных HA-установках. Сам Redis не поставляется в комплекте из-за его лицензии.
- Очередь скрыта за портом `JobQueue`, поэтому замена River в будущем затронет только один адаптер.

## Рассмотренные альтернативы

| Вариант | Почему нет |
|---|---|
| Redis + BullMQ | Node.js, а мы используем Go |
| Redis/Valkey + asynq | Дополнительный сервис с состоянием, нет транзакционной постановки в очередь вместе с нашей БД (проблема двойной записи, dual write), медленный цикл релизов |
| RabbitMQ | Дополнительный брокер с состоянием и операционная нагрузка, нет транзакционной постановки в очередь вместе с PostgreSQL (всё равно нужен outbox) |
| NATS JetStream | Отлично подходит для будущего обмена сообщениями с edge-площадками или агентами, но сегодня это лишний кластер и та же проблема двойной записи. Вернуться к вопросу для агентов парка или edge-агентов |
| Temporal | См. ADR-0008: слишком тяжёл для self-hosted и изолированных (air-gap) установок. Возможна необязательная интеграция в будущем |
| DBOS Transact Go (MIT, надёжные (durable) workflows на PostgreSQL) | Перспективная альтернатива в виде одной библиотеки, но молодая (1.x в 2026 году). Перед Phase 2 стоит провести исследовательский прототип (spike) как возможную замену частей нашего исполнителя (executor) |

## Последствия

- Плюсы: одна зависимость с состоянием, атомарные изменения состояния и заданий, более простые air-gap и HA, в установке по умолчанию нет хранилищ данных под копилефт- или source-available-лицензиями.
- Минусы: пропускная способность очереди ограничена PostgreSQL. Для нагрузок провижининга этого с запасом хватает (операции длительные и крупнозернистые), а для лимитов частоты запросов на уровне реплик в больших масштабах нужен Valkey. River ещё не достиг версии 1.0, поэтому обновлять его нужно осторожно.
