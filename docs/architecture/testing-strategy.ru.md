# Стратегия тестирования

> Статус: **Предложено** (Phase 0). Язык: [English](testing-strategy.md) · Русский
>
> Связанные документы: [ARCHITECTURE](../ARCHITECTURE.ru.md) · [Движок провижининга](provisioning-engine.ru.md) · [Модель угроз](../security/THREAT_MODEL.ru.md) · ADR-0016 (тестирование без собственного оборудования)

«Не пишите приложение без тестов» (промпт §61). Функциональность считается готовой только тогда, когда у неё есть тесты на нужном уровне (Definition of Done — критерии готовности, промпт §125). Этот документ определяет эти уровни, тестовые окружения, обязательный E2E-сценарий и матрицу тестирования сбоев. Он также описывает, как мы тестируем провижининг (provisioning) инфраструктуры, **не имея собственного оборудования**.

## 1. Пирамида тестов

| Аддоны | Установка/обновление/удаление/проверка состояния для каждого аддона и каждой версии каталога на **kind/k3d** | `make test-cluster` + Go-тесты, использующие Helm-сервис | ночные прогоны + при изменениях каталога | Каждая запись каталога протестирована до релиза |

## 2. Принципы

- **Реальные зависимости вместо моков** на интеграционном уровне: настоящий PostgreSQL, настоящий River, настоящий Helm SDK против настоящего кластера (kind/k3d), настоящий SSH-сервер в контейнерах. Моки используются только для внешних SaaS API (записанные фикстуры) и для внедрения сбоев.
- **Детерминированность:** время внедряется как зависимость (`Clock`), генератор случайных чисел инициализируется фиксированным seed, планы проверяются golden-файлами, а параллельное выполнение DAG тестируется в детерминированном режиме диспетчера.
- **Никакого фиктивного кода в продакшене:** симулированный провайдер и инжекторы сбоев находятся в чётко отделённых пакетах (`plugins/providers/simulated`, `test/…`), помечены метаданными `TestOnly` и отклоняются в продакшен-профилях (промпт §115).
- **Тесты — это документация:** каждый тест сценария сбоя проверяет видимый пользователю код ошибки, рекомендации по устранению и доступные действия, а не просто факт «возвращает ошибку».
- **Нестабильные (flaky) тесты — это баги:** чтобы поместить тест в карантин, нужны issue и ответственный, а срок карантина ограничен.

## 3. Тестовые окружения — тестирование без собственного оборудования

У владельца нет ни физических, ни виртуальных машин. Мы используем три уровня (tiers).

### 3.1 Tier 1 — симулированная инфраструктура (каждый PR, от секунд до минут)

- Провайдер `simulated` создаёт фиктивные хосты с настраиваемыми характеристиками (ОС, CPU, RAM, диск), задержками и **сценариями сбоев** (fault scripts): «сбой `runtime.install` на узле w-2 при первой попытке с временной ошибкой», «разрыв SSH-соединения через 3 с», «диск заполнен».
- Движок, API, SSE, UI и CLI работают по-настоящему. Симулируется только сторона узлов.
- Этот уровень подтверждает корректность логики оркестрации: порядок выполнения DAG, параллелизм, повторы, приостановку/возобновление, откат, отмену, восстановление после падения (завершение процесса воркера посреди операции), ключи идемпотентности, защиту от конкурентных операций.
- Здесь же выполняются E2E-тесты Playwright: режим Auto (Auto Mode) → план → развёртывание → прогресс в реальном времени → успех; сбой → отчёт → повтор → успех.

### 3.2 Tier 2 — контейнерные узлы (подмножество в каждом PR, полный набор ночью; минуты)

- **«Контейнерные узлы»** — это привилегированные Docker-контейнеры, в которых работают **systemd + sshd**, с базовым образом для каждой поддерживаемой ОС (Ubuntu 24.04/26.04, Debian 13; Rocky/Alma позже). Для kubeadm они достаточно похожи на ВМ — это доказывает проект `kind`, который запускает kubeadm внутри контейнеров.
- Платформа подключается к ним **по настоящему SSH** с одноразовыми сгенерированными ключами и запускает **настоящий слой bootstrap и драйвер kubeadm**: установку containerd и пакетов Kubernetes (из локального кеша/зеркала пакетов, чтобы CI работал быстро и мог работать офлайн), `kubeadm init/join` (конфигурации с одним узлом control plane и HA из 3 узлов control plane с kube-vip в Docker-сети), Cilium, затем аддоны. После этого выполняются проверки `kubectl get nodes` / `get pods -A`.
- Известные ограничения, которые задокументированы и учитываются в тестах через флаги возможностей (capability flags):
  - модули ядра и многие sysctl принадлежат ядру CI-хоста. Задачи распознают ситуацию «уже загружен / только для чтения в контейнере» и в тестовом профиле считают требование выполненным.
  - нет настоящего L2 для ARP у kube-vip и для L2-режима MetalLB между хостами. Мостовая сеть Docker подходит для тестов на одном хосте.
  - нет настоящих дисков для проверки производительности Longhorn/Ceph (только функциональные тесты).
  - вложенность cgroup v2 требует CI-хоста с cgroup v2 (GitHub-hosted раннеры Ubuntu используют cgroup v2).
- Этот уровень ловит большинство реальных ошибок bootstrap (пакеты, конфигурационные файлы, флаги kubeadm, порядок присоединения узлов, идемпотентность при повторном запуске) без какого-либо облачного аккаунта.

### 3.3 Tier 3 — реальные виртуальные машины (ночью или вручную; десятки минут)

- Вариант A (рекомендуется, как только появится бюджет): **проект в Hetzner Cloud**, который CI использует через токен, хранящийся как секрет GitHub Actions; ВМ создаются и удаляются в каждом прогоне, а расходы ограничены. Так проверяются реальная сеть, реальные ядра, ARP у kube-vip в Hetzner vSwitch или ограничения частной сети (и подтверждается, почему L2-режим MetalLB не работает в Hetzner Cloud), реальные диски для Longhorn и сам провайдер Hetzner из фазы 7.
- Вариант B: **вложенные ВМ на CI-раннерах** (QEMU/KVM, если раннер предоставляет `/dev/kvm`) с облачными образами и cloud-init. Это медленнее, зато без счёта за облако, и подходит для smoke-тестов по матрице ОС.
- Вариант C: владелец или контрибьюторы запускают `make e2e-real` на любых доступных им по SSH машинах, используя ту же обвязку.
- Пока Tier 3 не запускается, отчёты по фазам явно указывают, какие сценарии проверены только на Tier 1–2 (**никаких заявлений «протестировано на bare metal» без доказательств**).

### 3.4 Локальные окружения разработчика

- `make dev`: docker compose с PostgreSQL, api, worker и dev-сервером Vite (в dev-профиле включён симулированный провайдер).
- `make test-cluster`: создаёт локальный кластер **kind** (по умолчанию) или **k3d** (`TEST_CLUSTER=k3d`) для тестов аддонов и Helm-сервиса (промпт §78).
- `make test-nodes`: локально запускает N контейнерных узлов для тестов Tier 2.
- `make e2e`: запускает E2E-тесты Tier 1 (UI + API) в headless-режиме.

## 4. Обязательный E2E-сценарий (промпт §62)

```
Create cluster (UI / API / CLI)
  → Provision infrastructure (simulated | container nodes | real VMs)
  → Install Kubernetes (kubeadm)
  → Install CNI (Cilium)
  → Install Gateway API controller
  → Install storage (local-path; Longhorn on Tier 3)
  → Install monitoring (kube-prometheus-stack)
  → Health check
  → Cluster READY
  → Get kubeconfig (user-scoped)
  → kubectl get nodes            (all Ready, expected roles/versions)
  → kubectl get pods -A          (no CrashLoopBackOff; add-on pods Ready)
  → Deploy sample app behind a Gateway + HTTPRoute, curl it (Tier 2/3)
  → Delete cluster → nodes reset, records DESTROYED, audit complete
```

Обвязка также проверяет записи журнала аудита, события операций (отсутствие секретов — сканирование на canary-значения), доставку вебхуков (на локальный приёмник) и состояние UI после перезагрузки браузера посреди развёртывания (промпт §66).

## 5. Матрица тестирования сбоев (промпт §63)

Каждый сценарий выполняется как минимум на Tier 1 (внедрение сбоев). Сценарии, отмеченные ★, выполняются также на Tier 2 с реальными сбоями (остановка sshd, заполнение tmpfs, отбрасывание пакетов через iptables, завершение контейнеров).

| Сценарий | Внедрение | Ожидаемое поведение |
|---|---|---|
| Сбой SSH ★ | Остановить sshd / разорвать соединение посреди команды | Повтор при временной ошибке с backoff; после исчерпания попыток — PAUSED с `SSH_UNREACHABLE` (что/почему/где/как исправить); после восстановления sshd возобновление (Resume) работает |
| Узел недоступен ★ | Завершить контейнер узла до или во время присоединения | Предварительные проверки (preflight) выявляют проблему до начала; посреди операции → задача завершается с `NODE_UNREACHABLE`; остальные узлы продолжают работу до безопасной точки |
| Диск заполнен ★ | Маленький tmpfs на `/var/lib/containerd` | Предварительные проверки предупреждают о нехватке места; установка среды выполнения завершается с `DISK_FULL` и рекомендацией (освободить место / увеличить диск) |
| Неверные учётные данные | Неверный ключ / пароль / sudo требует пароль | `SSH_AUTH_FAILED` / `SUDO_PASSWORD_REQUIRED` (UserAction, без повторов), в рекомендации — ссылка на учётные данные |
| Сеть недоступна ★ | iptables DROP между узлами / к зеркалу пакетов | `PACKAGE_REPO_UNREACHABLE` или `K8S_JOIN_API_UNREACHABLE` с проверками портов/маршрутов |
| Сбой Helm | Ошибка рендеринга чарта / тайм-аут / сбой хука | Задача аддона завершается сбоем; при политике `rollback` → helm rollback; в отчёте — чарт, diff values и ресурс, вызвавший сбой |
| Сбой аддона | Поды аддона в CrashLoop (неверные values) | Проверка состояния не проходит → откат только этого аддона (обратимая операция); кластер остаётся работоспособным |
| Сбой bootstrap Kubernetes ★ | `kubeadm init` завершается ошибкой (порт занят, неверная конфигурация) | Обработка необратимого шага: PAUSED, рекомендации, `ResetNode` предлагается явно |
| Частичное развёртывание | Завершать процесс воркера в случайные моменты (100 итераций) | Аренда (lease) истекает → другой воркер возобновляет работу; ни одна задача не выполняется дважды одновременно; итоговое состояние идентично прогону без прерываний |
| Сбой присоединения рабочего узла ★ | Заблокировать порт 6443 для одного рабочего узла | Сбоят только задачи этого узла; кластер READY с WARNING, если политика допускает частичный результат, иначе PAUSED; повтор (Retry) для этого узла работает |
| Сбой присоединения узла control plane ★ | Сломать peer-порт etcd на cp-2 | Последовательное присоединение узлов control plane останавливается; задача очистки члена etcd задокументирована; кворум на cp-1 не теряется |
| БД недоступна | Приостановить контейнер PostgreSQL | API возвращает 503 на проверке готовности (readiness); воркеры перестают запускать задачи и удерживают аренды до тайм-аута; операции возобновляются после возвращения БД |
| Повторная отправка | Один и тот же Idempotency-Key дважды, одновременно | Ровно одна операция |
| Конкурентная операция | Запустить обновление во время выполнения apply | `409 OPERATION_IN_PROGRESS` |

Каждый тест сбоя проверяет: код ошибки, локализованные заголовок и рекомендацию (en и ru), `location` (задача/узел), доступные действия (Retry/Resume/Rollback), отсутствие секретов в сообщениях, корректную фазу кластера и событие аудита.

## 6. Тестирование безопасности

- **Матрица авторизации**: генерируется из спецификации OpenAPI и каталога разрешений. Для каждой комбинации «эндпоинт × встроенная роль × (тот же тенант, другой тенант, анонимный пользователь)» проверяется ожидаемый статус (200/202, 403, 404, 401).
- **Выход за пределы тенанта**: для каждого репозитория и каждого эндпоинта — с id из другой организации, включая подписку на SSE и её возобновление, логи, аудит, поиск и kubeconfig.
- **SSRF**: URL на loopback, частные диапазоны, IP-адреса сервисов метаданных, DNS-имена, разрешающиеся в частные IP, редиректы на частные IP, трюки с IPv6 (`::ffff:127.0.0.1`), симуляция DNS rebinding.
- **Инъекции**: фаззинг валидаторов (имена хостов, метки, пути, версии) и функции POSIX-экранирования против настоящего `/bin/sh` в изолированном контейнере. Проверяемое свойство: произвольный ввод должен доходить до удалённой программы ровно одним аргументом.
- **Утечка секретов**: canary-секреты (уникальные случайные строки) в учётных данных. После каждого E2E-прогона canary-значения ищутся в таблицах БД (кроме `secrets`), логах, событиях, ответах API, payload вебхуков и отчётах об ошибках.
- **Сканирование зависимостей и образов**: govulncheck, OSV-Scanner или Grype для зависимостей Go и npm, сканирование наших образов, diff SBOM для каждого релиза.
- **Заголовки и сессии**: автоматические проверки CSP, HSTS, флагов cookie, обязательности CSRF-токена, ротации сессий и тайм-аутов.

## 7. Подробности тестирования фронтенда

- **Компонентные тесты** для дизайн-системы и доменных виджетов (TaskTree, LogViewer, SpecDiff, StatusBadge, формы на основе схем) с проверками axe в обеих темах.
- **Интеграционные тесты** с MSW: мастер (валидация, возврат назад, зависимые поля, сохранение черновика), режим Auto (объяснения, переопределения, предупреждения), представление операции (воспроизведение SSE и режим реального времени), формы учётных данных (поведение write-only) и отображение ошибок из problem+json.
- **E2E на Playwright** против стека docker compose с симулированным провайдером. Покрывают критичные пути в Chromium (все PR), Firefox и WebKit (ночные прогоны), навигацию только с клавиатуры и скриншоты светлой/тёмной темы для визуального ревью.
- **Проверки i18n**: отсутствие недостающих ключей в `ru`, прогон с псевдолокалью для выявления захардкоженных строк и обрезки текста.

## 8. CI-конвейер (промпт §80)

```
lint ─▶ unit ─▶ integration ─▶ build ─▶ security scan ─▶ e2e (simulated; container-nodes subset) ─▶ docker build ─▶ publish (tags only: signed images/binaries, SBOM, provenance)
                                                     nightly: full container-nodes matrix, add-on matrix on kind/k3d, browser matrix, fuzzing (time-boxed), Tier 3 when configured
```

- Обязательные проверки для `main`: lint, unit, integration, build, security scan, E2E simulated.
- Кеширование: кеш сборки Go, хранилище pnpm, зеркало пакетов для контейнерных узлов, кеш образов.
- Отчёты о тестах (JUnit), покрытие и трейсы Playwright загружаются как артефакты. Из сбоев есть ссылки на логи.

## 9. Definition of Done — требования к тестированию

Изменение считается готовым, только если: модульные тесты покрывают новую логику; интеграционные тесты покрывают новые эндпоинты/репозитории (включая авторизацию и изоляцию тенантов); для путей сбоя есть тесты, проверяющие видимые пользователю ошибки; E2E обновлён, если изменился пользовательский сценарий; тесты безопасности обновлены, если изменение затрагивает угрозу из [модели угроз](../security/THREAT_MODEL.ru.md); lint, проверка типов и форматирование проходят; `make dev` по-прежнему работает; а отчёт по фазе честно указывает, на каких уровнях (tiers) изменение проверено.
