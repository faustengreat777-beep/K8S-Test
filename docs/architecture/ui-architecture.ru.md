# Архитектура UI

> Статус: **Предложено** (Phase 0). Язык: [English](ui-architecture.md) · Русский
>
> Связанные документы: [ARCHITECTURE](../ARCHITECTURE.ru.md) · [Проектирование API](api-design.ru.md) · [Режим Auto, каталог и совместимость](auto-mode-and-catalog.ru.md) · ADR-0012 (стек фронтенда)

Веб-интерфейс — **лишь один из клиентов публичного API** (промпт §57). В нём нет бизнес-правил, которые не обеспечивал бы и сервер, и нет критичного состояния, которое существовало бы только в браузере (промпт §89). Его задача — сделать так, чтобы сложной системой было просто пользоваться. Интерфейс должен быть «простым по умолчанию и мощным, когда это нужно» (промпт §119) и выглядеть как современный продукт, а не как старая админ-панель (промпт §44).

## 1. Стек

| Аспект | Выбор | Примечания |
|---|---|---|
| Язык / фреймворк | TypeScript (strict) + React | Функциональные компоненты, хуки, никаких классовых компонентов |
| Сборка | Vite | Dev-сервер проксирует `/api` на Go-сервер; продакшен-сборка встраивается в Go-бинарник через `go:embed` |
| Стили | Tailwind CSS v4 + CSS-переменные в роли дизайн-токенов | Токены задаются один раз для светлой и тёмной тем |
| Компоненты | shadcn/ui (скопирован в `web/src/components/ui` и принадлежит нам) поверх доступных (accessible) примитивов | Можно менять стили и расширять компоненты без стороннего UI-кита |
| Маршрутизация | TanStack Router (маршруты на основе файлов, типобезопасные search-параметры) | Search-параметры хранят фильтры и пагинацию, поэтому представлениями можно делиться и их можно восстановить |
| Серверное состояние | TanStack Query | Единый кеш данных API; события SSE обновляют кеш; оптимистичный UI — только для дешёвых и обратимых действий |
| Формы | React Hook Form + Zod | Схемы Zod по возможности **генерируются** из OpenAPI/JSON Schema, поэтому клиентская валидация совпадает с серверной |
| API-клиент | Генерируется из OpenAPI (типы `openapi-typescript` + небольшая обёртка над fetch) | Никаких написанных вручную типов запросов |
| YAML / код | Monaco Editor + `monaco-yaml` (валидация по JSON Schema, автодополнение, документация при наведении) + diff-редактор Monaco | Загружается лениво (большой бандл) и только на тех маршрутах, где он нужен |
| Логи в стиле терминала | xterm.js для необработанного вывода команд; виртуализированная таблица структурированных логов (TanStack Virtual) для событий | Логи одной операции могут достигать 100 тыс. строк |
| Палитра команд | `cmdk` | Ctrl/Cmd + K |
| i18n | i18next + формат сообщений ICU | en и ru с первого дня; правила множественного числа для русского языка обрабатывает ICU |
| Графики | Лёгкие SVG-графики (загрузка ресурсов, история) | Следуют дизайн-токенам; никаких тяжёлых BI-библиотек |
| Тесты | Vitest + Testing Library + MSW; Playwright E2E; проверки доступности axe-core | См. [стратегию тестирования](testing-strategy.ru.md) |

Точные версии указаны в документе [«Технологический стек»](technology-stack.ru.md).

## 2. Структура исходного кода

```
web/
├── index.html
├── src/
│   ├── app/                    # router, providers (QueryClient, i18n, theme), layout shell, error boundaries
│   ├── routes/                 # route files (TanStack Router file-based routing)
│   ├── features/
│   │   ├── auth/               # login, session expiry handling
│   │   ├── clusters/           # list, dashboard, settings, YAML view, spec history/diff
│   │   ├── create/             # Auto / Simple / Advanced creation flows, review, deploy
│   │   ├── operations/         # live progress, task tree, logs, failure report, actions
│   │   ├── nodes/              # node list/detail, cordon/drain/replace
│   │   ├── addons/             # catalog browser, install/configure/remove
│   │   ├── templates/          # templates and versions
│   │   ├── credentials/        # vault (write-only secret forms)
│   │   ├── providers/          # provider accounts, inventory
│   │   ├── audit/              # audit log search/export
│   │   ├── settings/           # org, members, roles, API keys, webhooks, notifications
│   │   └── search/             # global search, command palette
│   ├── components/
│   │   ├── ui/                 # design-system primitives (shadcn-based)
│   │   └── domain/             # reusable domain widgets: StatusBadge, HealthPill, TaskTree, LogViewer, SpecDiff, PlanSummary…
│   ├── lib/
│   │   ├── api/                # generated client + query keys + hooks
│   │   ├── sse/                # EventSource wrapper with Last-Event-ID resume and backoff
│   │   ├── schema/             # JSON Schema → form helpers, Zod generation glue
│   │   └── format/             # dates, durations, bytes, percentages (locale-aware)
│   ├── i18n/
│   │   ├── en/*.json
│   │   └── ru/*.json
│   └── styles/                 # tokens.css (light/dark), tailwind entry
└── tests/                      # Playwright E2E
```

Правила: функциональные модули (features) не импортируют внутренние части друг друга. Общий код размещается в `components/domain` или `lib`. Каждый модуль владеет своими маршрутами, компонентами, хуками и пространством имён i18n.

## 3. Информационная архитектура

```
Top bar:  org/project switcher · global search · command palette · notifications · help · user menu (theme, language)
Sidebar:  Overview · Clusters · Operations · Templates · Add-on catalog · Credentials · Providers · Audit · Settings
          (enterprise later: Fleet · Policies · Change requests · Compliance · Incidents · Cost)
```

Основные экраны:

| Экран | Содержимое |
|---|---|
| **Обзор** (Overview; несколько кластеров, промпт §37) | Карточки или таблица кластеров с фазой и состоянием (Production HEALTHY, Staging HEALTHY, Development WARNING…), выполняющиеся операции, недавние сбои, предупреждения об истечении срока действия сертификатов |
| **Дашборд кластера** (промпт §31) | Статус, версия Kubernetes, количество узлов/подов/пространств имён, загрузка CPU/памяти/диска (если доступны метрики), состояние каждой подсистемы (control plane, сеть, хранилище, gateway, мониторинг, резервное копирование), эндпоинты (API, Grafana), скачивание kubeconfig, быстрые действия |
| **Узлы** (Nodes; промпт §30) | Группировка по ролям: control plane / рабочие узлы (workers) / пулы; для каждого узла — CPU, RAM, диск, IP, ОС, версия kubelet, статус, условия (conditions), поды, загрузка; действия: cordon, drain, перезапуск, удаление, замена |
| **Операции** (Operations) | История с фильтрами; представление операции в реальном времени (раздел 6) |
| **Аддоны** (Add-ons) | Установленные аддоны с состоянием и версией; карточки каталога с описанием, плюсами и минусами, совместимостью, сценариями использования (промпт §17); настройка через форму, построенную по схеме, или через YAML |
| **Настройки → Конфигурация** (Settings → Configuration) | Расширенное дерево настроек (промпт §4): Общие, Kubernetes, Control Plane, Рабочие узлы, Сеть, DNS, Среда выполнения контейнеров, Хранилище, Gateway/Ingress, Балансировщик нагрузки, Сертификаты, Безопасность, Наблюдаемость, Логирование, Резервное копирование, GitOps, Автомасштабирование, GPU, Реестр, Аддоны, Планирование, Политики, Дополнительно — с вкладкой **YAML** и вкладкой **История/Сравнение** |
| **Обновление** (Upgrade) | Советник по обновлению (upgrade advisor): текущая версия против целевой, совместимость, предварительные проверки (preflight), план, возможный простой, предупреждения → подтверждение |

## 4. Создание кластера: три режима, одна модель

Все режимы формируют одну и ту же **ClusterSpec** и завершаются одним и тем же шагом **Проверка → План → Развёртывание** (Review → Plan → Deploy). При переключении режима данные сохраняются. Пользователь может начать в режиме Auto, открыть «Настроить» (Simple/Advanced), а затем отредактировать YAML — и ничего не потеряется.

### 4.1 Режим Auto (Auto Mode; точка входа по умолчанию, промпт §127, §234)

1. Короткая форма: **Имя, Инфраструктура (аккаунт провайдера или «добавить хосты»), Окружение, Размер, Доступность**. Необязательный блок «Дополнительные параметры»: тип рабочей нагрузки, бюджет, требования соответствия (compliance), регион.
2. «Анализ инфраструктуры…» → по мере выполнения появляются результаты проверок (доступность провайдера, ёмкость региона, совместимость с Kubernetes).
3. «Формирование плана кластера…» → карточка рекомендации: Kubernetes, control plane, рабочие узлы, CNI, Gateway, LB, хранилище, мониторинг, логирование, TLS, резервное копирование, профиль безопасности, оценка стоимости (или «Оценка стоимости недоступна»), оценка времени.
4. У каждой строки есть кнопка **[Почему?]** (Why?): всплывающее окно с причинами от движка принятия решений («Выбрано, потому что: продакшен-окружение, запрошена HA, включены сетевые политики…»). Есть и кнопка **[Изменить]** (Change): пользователь выбирает альтернативу, движок пересчитывает рекомендацию и подсвечивает зависимые изменения (промпт §131).
5. Предупреждения о безопасности показываются прямо в форме, с явным выбором («Вы выбрали 1 узел control plane для продакшен-кластера… [Всё равно продолжить] [Включить HA]», промпт §132).
6. «Проверка политик…» → **Развернуть** (Deploy).

### 4.2 Режим Simple (Simple Mode; промпт §3)

Создать кластер → Выбрать инфраструктуру → Выбрать пресет (Development, Staging, Production, High Availability, Minimal, Edge, GPU, AI/ML, Custom) → Проверка (настройка нескольких параметров) → Развёртывание.

### 4.3 Мастер режима Advanced (Advanced Mode; промпт §46)

Шаги: 1 Основное · 2 Инфраструктура · 3 Kubernetes · 4 Узлы · 5 Сеть · 6 Балансировщик нагрузки · 7 Хранилище · 8 Gateway (Ingress) · 9 Безопасность · 10 Наблюдаемость · 11 Резервное копирование · 12 GitOps · 13 Аддоны · 14 Проверка · 15 Развёртывание.

Мастер:
- **сохраняет черновик на сервере** после каждого шага (`PUT /clusters/{id}/spec` для кластера в состоянии DRAFT). Закрытие вкладки ничего не теряет, а черновики отображаются в разделе «Кластеры».
- **валидирует каждый шаг**: сначала на клиенте через Zod (мгновенно), затем на сервере через `POST /validate` (совместимость и политики, с debounce). Ошибки блокируют переход дальше, предупреждения показываются, но не блокируют.
- **позволяет свободно возвращаться** назад. Индикатор шагов (stepper) показывает, какие шаги заполнены и где есть проблемы.
- подставляет **разумные значения по умолчанию** из выбранного пресета или рекомендации.
- **скрывает или отключает несовместимые параметры** и объясняет причину. Например, при k3s и Flannel переключатель «Сетевые политики» показывает подсказку «требуется CNI с поддержкой NetworkPolicy».
- показывает **поля с учётом зависимостей** (промпт §47):
  - CNI = Cilium → Hubble, замена kube-proxy, шифрование (WireGuard/IPsec), Gateway через Cilium
  - Хранилище = Longhorn → число реплик, StorageClass по умолчанию, целевое хранилище резервных копий
  - Gateway = Envoy Gateway / NGINX Gateway Fabric → тип сервиса (LoadBalancer/NodePort), TLS (issuer), listeners
  - Балансировщик нагрузки = MetalLB → пулы адресов, режим L2/BGP, BGP-пиры
  Эти поля описаны в JSON Schema аддонов (`if/then/else`, `dependentSchemas`) и отрисовываются слоем «схема → форма»; для самых важных шагов используются компоненты, написанные вручную.

### 4.4 Режим YAML (промпт §34)

- Разделённое представление: форма ↔ YAML (Monaco). Правки на любой стороне сразу отражаются на другой. YAML разбирается и проверяется по JSON Schema для ClusterSpec из `/schemas/cluster-spec`.
- Неизвестные поля, ошибки типов и недопустимые значения enum подчёркиваются и сопровождаются сообщениями. Автодополнение и документация при наведении берутся из схемы.
- Перед сохранением показывается **diff** (текущая ревизия против новой, промпт §97). При сохранении выполняется форматирование.

### 4.5 Проверка и развёртывание (промпт §35, §65)

- Сводка плана (`POST /clusters/{id}/plan`): `+ 3 control plane nodes`, `+ Kubernetes 1.36.x`, `+ Cilium`, … Оценки времени и стоимости берутся из плана.
- Чек-лист: ✓ Конфигурация корректна · ✓ Инфраструктура доступна · ✓ Учётные данные действительны · ✓ Совместимость проверена · ✓ Необходимые ресурсы доступны. Каждый пункт ведёт к подробностям.
- Необратимые или рискованные шаги требуют явного подтверждения.
- Кнопка **[Развернуть кластер]** (Deploy Cluster) отправляет `POST /clusters/{id}/deploy` с `Idempotency-Key` и `planHash`, а затем переходит к представлению операции в реальном времени.

## 5. Правила управления состоянием

- **Источник истины — бэкенд.** Серверные данные хранятся только в кеше TanStack Query. Ключи запросов повторяют ресурсы API (`['cluster', id]`, `['operation', id, 'tasks']`).
- **URL хранит состояние представления**: фильтры, сортировку, пагинацию, выбранную вкладку, выбранную задачу. Перезагрузка страницы или переход по ссылке восстанавливают представление.
- **Локальное состояние компонентов** — только для эфемерного UI: открытых диалогов, несохранённого ввода до срабатывания debounce.
- **Никаких секретов в состоянии браузера**: формы учётных данных отправляют данные и сразу очищают поля. API никогда не возвращает секреты.
- **Устойчивость**: при переподключении или возврате фокуса запросы выполняются заново. SSE возобновляется с последнего id события. Приложение показывает неблокирующий баннер «Соединение потеряно — переподключение».
- **Восстановление после закрытия браузера** (промпт §66): при открытии кластера с активной операцией показывается «Идёт развёртывание», и UI подключается к потоку событий. История воспроизводится с сервера.

## 6. Представление операции в реальном времени (промпт §15)

```
Deploying "production"                                    ⏱ 08:41 elapsed · ~6 min remaining
[✓] Validating infrastructure
[✓] Preparing nodes (6/6)
[✓] Installing containerd
[✓] Installing Kubernetes
[✓] Bootstrapping control plane
[✓] Installing Cilium
[✓] Installing CoreDNS
[→] Installing Gateway (Cilium)            ▸ 3 tasks
[ ] Installing cert-manager
[ ] Installing monitoring
[ ] Running health checks
───────────────────────────────────────────────────────────────────────────────
Logs  [All levels ▾] [All tasks ▾] [All nodes ▾] [Search…]          [Follow ✓] [Download]
12:31:02 INFO  cp-1  Connecting to node 10.0.0.11
12:31:03 INFO  cp-1  Installing containerd
12:31:08 INFO  cp-1  containerd installed
```

- **Дерево задач** группирует задачи DAG (граф задач) в понятные пользователю этапы (соответствие задач этапам берётся из метаданных задач). При раскрытии этапа видны задачи по каждому узлу с попытками и длительностью.
- **Панель логов** виртуализирована: фильтры по уровню, задаче и узлу, полнотекстовый поиск (на сервере — по истории, на клиенте — по логам, поступающим в реальном времени), режим слежения (follow) и скачивание (JSON или текст).
- **Состояние сбоя**: карточка отчёта о сбое (что / почему / где / как исправить) с кнопками действий: Повторить (Retry), Возобновить (Resume), Откатить (Roll back), Просмотреть логи (View logs), Прервать (Abort). Логи заранее отфильтрованы по упавшей задаче.
- **Состояние успеха**: «🎉 Кластер готов» с URL Kubernetes API, URL Grafana и подсказкой по учётным данным (секрет можно получить один раз, либо вход через SSO), кнопками **Скачать kubeconfig** и **Открыть кластер**.

## 7. Дизайн-система

Компоненты (промпт §45): кнопки, поля ввода, выпадающие списки (select), комбобоксы, диалоги, выдвижные панели (drawers), таблицы (с сортировкой, выбором строк, виртуализацией), карточки, бейджи (фаза/состояние), оповещения (alerts), индикаторы прогресса (линейный, stepper, дерево задач), мастер/stepper, просмотрщик логов, терминал, редактор кода, редактор YAML, просмотрщик diff, пустые состояния (empty states), skeleton-загрузчики, всплывающие уведомления (toasts), палитра команд.

- **Токены** (`styles/tokens.css`): цветовые роли (`--bg`, `--surface`, `--text`, `--muted`, `--primary`, `--success`, `--warning`, `--danger`, `--info`, `--border`, `--focus-ring`), отступы, радиусы скругления, типографика, уровни возвышения (elevation), анимация (motion). Светлый и тёмный наборы проектируются отдельно и проверяются на контрастность. Тёмный режим — полноценная тема, а не инвертированные цвета (промпт §95). По умолчанию тема следует настройке ОС; пользователь может её переопределить.
- **Семантика статусов** везде одинакова: бейджи фаз (READY, UPDATING, PAUSED, FAILED…) и индикаторы состояния (HEALTHY/WARNING/CRITICAL/UNKNOWN) всегда дополняют цвет иконкой и подписью — один лишь цвет никогда не используется.
- **Плотность**: по умолчанию комфортная, компактная — для таблиц узлов, логов и аудита.
- **Тексты**: в первую очередь простой язык, технические подробности — по запросу («Показать технические подробности»).

## 8. Доступность (промпт §90)

Цель — **WCAG 2.2 AA**:
- Полная навигация с клавиатуры (логичный порядок табуляции, видимое кольцо фокуса, никаких клавиатурных ловушек, сочетания клавиш перечислены в диалоге справки и в палитре команд).
- Корректные метки и описания для каждого элемента формы. Ошибки связаны с полями через `aria-describedby`.
- Управление фокусом: диалоги удерживают фокус внутри себя и возвращают его при закрытии. При смене маршрута фокус переходит на заголовок страницы.
- Скринридеры: live-регионы объявляют ключевые этапы выполнения операции и сбои, не зачитывая каждую строку лога.
- Достаточная контрастность в обеих темах. Учитывается `prefers-reduced-motion`.
- Автоматические проверки axe в компонентных тестах и в Playwright, а также ручная проверка со скринридером перед каждым крупным релизом.

## 9. Адаптивность (промпт §91)

Десктоп поддерживается в первую очередь, планшеты (≥ 768 px) — полностью. На экранах меньше этого работают представления только для чтения (статус, операции, уведомления), а сложное редактирование, например мастер и YAML, показывает подсказку «удобнее на большом экране», но остаётся пригодным к использованию.

## 10. Интернационализация (промпт §92)

- i18next с отдельным пространством имён для каждого функционального модуля. Формат сообщений — ICU (`{count, plural, one {# node} few {# узла} many {# узлов} other {# узла}}`).
- Коды ошибок сервера сопоставляются с локализованными сообщениями. API тоже локализует `title`/`detail` по `Accept-Language`, но UI ради единообразия предпочитает собственный каталог сообщений.
- Даты, числа, длительности и размеры в байтах форматируются через `Intl` с учётом локали пользователя. Всё время отображается в локальном часовом поясе, а при наведении — в UTC.
- Исходный язык — английский. Русский перевод обновляется в том же PR, что и любое изменение текстов (CI падает, если ключи отсутствуют). Чтобы добавить язык, достаточно добавить папку.

## 11. Глобальный поиск и палитра команд (промпт §93–94)

- **Поиск** (`/` или верхняя панель): кластеры, узлы, операции, аддоны, логи, пользователи — через `GET /search`. Результаты группируются по типу и фильтруются на сервере по правам пользователя.
- **Палитра команд** (Ctrl/Cmd + K): действия вроде «Создать кластер», «Открыть production», «Просмотреть развёртывания», «Добавить узел», «Установить аддон», «Обновить Kubernetes» и «Скачать kubeconfig». Команды регистрируются функциональными модулями с проверкой прав и контекста; недоступные команды объясняют, почему они недоступны.

## 12. Бюджет производительности

- Начальный JS оболочки приложения ≤ 250 KB в gzip. Monaco, xterm.js и графики загружаются ленивыми чанками.
- Time to interactive для дашборда на ноутбуке среднего класса ≤ 2 с (при кешированном API).
- Списки пагинируются на сервере, а длинные — ещё и виртуализируются на клиенте.
- Обновления SSE группируются по кадрам анимации, чтобы отрисовка оставалась плавной в «шумных» фазах.

## 13. Безопасность в UI

- Только same-origin: UI отдаёт тот же бинарник, что и API. Cookies помечены `HttpOnly`, а CSRF-токен передаётся в заголовке.
- Строгая **Content-Security-Policy** без inline-скриптов. Веб-воркеры Monaco загружаются с того же origin.
- Секреты не отображаются и не хранятся. Поля ввода учётных данных используют `autocomplete="off"`, где это уместно.
- Внешние ссылки (URL Grafana, документация) используют `rel="noopener noreferrer"`.
- Строки, введённые пользователем, всегда отображаются как текст и никогда — как HTML. Markdown (например, документация аддонов из каталога) отображается через санитайзер.
