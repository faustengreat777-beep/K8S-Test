# Модель безопасности

> Статус: **Предложено** (Phase 0). Язык: [English](SECURITY_MODEL.md) · Русский
>
> Связанные документы: [Модель угроз](THREAT_MODEL.ru.md) · [ARCHITECTURE](../ARCHITECTURE.ru.md) · [Модель данных](../architecture/data-model.ru.md) · [Проектирование API](../architecture/api-design.ru.md) · ADR-0011 (мультитенантность), ADR-0014 (секреты и шифрование), ADR-0015 (удалённое выполнение)

Farvater хранит ключи от инфраструктуры своих пользователей: SSH-ключи с правами root, токены облачных API, административные учётные данные кластеров, ключи от хранилищ резервных копий. Компрометация платформы означает компрометацию каждого кластера, которым она управляет. Поэтому безопасность — первоочередная задача проектирования начиная с фазы 1, а не дополнение для редакции Enterprise (промпт §54, §99).

## 1. Принципы

| Принцип | Что это значит в продукте |
|---|---|
| Минимальные привилегии | Каждый субъект (пользователь, API-ключ, сервисный аккаунт, воркер, роль БД, компонент платформы) получает минимально необходимые разрешения; API-ключи могут только сужать права своего владельца; роли БД разделены (`app`, `app_system`, `app_owner`) |
| Запрет по умолчанию | Нет разрешения — нет доступа; неизвестные маршруты, поля и значения перечислений отклоняются; исходящие сетевые подключения к частным диапазонам запрещены, если они не внесены в список разрешённых |
| Эшелонированная защита | Авторизация на уровне приложения **и** Row-Level Security в PostgreSQL; валидация входных данных **и** типизированные команды **и** отсутствие интерполяции в shell; шифрование **и** контроль доступа **и** аудит |
| Безопасные настройки по умолчанию | TLS везде, проверка ключей хостов включена, усиленный (hardened) профиль кластера для продакшена, PodSecurity `restricted`, предлагаемые NetworkPolicy с запретом по умолчанию (default-deny), шифрование секретов при хранении (at rest) в кластерах, короткоживущие kubeconfig |
| Нулевое доверие (zero trust), где это возможно | Каждый запрос аутентифицируется и авторизуется; внутренние соединения (API ↔ БД, воркер ↔ узлы) шифруются и аутентифицируются; никакого неявного доверия на основании расположения в сети |
| Секреты — сущность первого класса | Выделенное хранилище секретов с конвертным шифрованием (envelope encryption), поля API только для записи (write-only), маскирование везде, расшифровка just-in-time и только в воркерах |
| Проверяемость (auditability) | Каждое значимое для безопасности действие записывается в журнал только для добавления (append-only) с указанием актора, источника, цели и результата |
| Минимальная поверхность атаки | Один бинарный файл, мало зависимостей, никакой загрузки плагинов во время выполнения, никакого выполнения произвольных скриптов, метрики на отдельном listener |

## 2. Границы доверия

```
 Internet / corporate network
   │  (TLS)
   ▼
┌───────────────────────┐   Boundary A: untrusted clients → API
│ api role              │   authn, CSRF, rate limits, input validation, authz, audit
│ (no infra credentials)│
└──────────┬────────────┘
           │ PostgreSQL (TLS, role `app`, RLS)          Boundary B: app ↔ database
┌──────────▼────────────┐
│ PostgreSQL            │   encrypted secret blobs only; KEK never stored here
└──────────▲────────────┘
           │ jobs (River) + leases
┌──────────┴────────────┐   Boundary C: worker holds decrypted credentials transiently
│ worker role           │   KEK access (local key file / KMS), SSRF-guarded egress
└───┬─────────┬─────────┘
    │ SSH     │ HTTPS (provider APIs, K8s API, Helm/OCI registries, Git, webhooks)
    ▼         ▼                                         Boundary D: platform → customer infrastructure
 Customer nodes & clusters, cloud provider APIs, external services
```

Следствия для архитектуры:
- Роль **api никогда не хранит учётные данные инфраструктуры и никогда не подключается к инфраструктуре клиента**. Она не может расшифровывать секреты с учётными данными. Конвертная расшифровка подключена только к `SecretAccessor` воркера. Единственное исключение — подпись вебхуков для *исходящих* событий платформы, которую выполняет воркер. Даже если уровень API скомпрометирован, у атакующего всё равно нет ключей в открытом виде.
- Воркеры могут работать в отдельной сетевой зоне: исходящий трафик — только к инфраструктуре клиентов и к базе данных, входящего нет вовсе.
- KEK (ключ шифрования ключей) никогда не хранится в PostgreSQL. Он берётся из файла или переменной окружения, смонтированных только в воркеры (редакция Community), либо из внешнего KMS/движка Transit (редакция Enterprise).

## 3. Идентификация и аутентификация

**Пользователи (браузер)**
- Локальные учётные записи (фаза 1): email + пароль, хешированный с помощью **argon2id** (память ≥ 64 MiB, итераций ≥ 3, параллелизм 1–4, соль 16 байт; параметры версионируются в строке PHC, и при их изменении пароль перехешируется при входе). Минимальная длина — 12 символов, проверка по списку скомпрометированных паролей (опционально — range API с k-анонимностью или офлайн-список), без требований к составу символов.
- Сессии: случайный 256-битный токен в cookie `__Host-session` (`HttpOnly; Secure; SameSite=Lax; Path=/`). Хранится только его SHA-256. Тайм-аут бездействия (по умолчанию 30 мин) и абсолютное время жизни (по умолчанию 12 ч). Идентификатор сессии меняется при входе и при изменении привилегий. Пользователи могут просматривать и отзывать свои сессии, а администраторы — отзывать все сессии пользователя.
- CSRF: токен-синхронизатор (synchronizer token), привязанный к сессии и обязательный в `X-CSRF-Token` для небезопасных методов. `SameSite=Lax` добавляет второй уровень защиты. CORS по умолчанию отключён.
- Защита входа: экспоненциальная задержка (backoff) для каждой учётной записи и каждого IP, временная блокировка после серии неудачных попыток (с событием аудита), обезличенные сообщения об ошибках, сравнение за постоянное время.
- Фаза 9 / ee: MFA (TOTP, WebAuthn/passkeys) с административной политикой «MFA обязательна», SSO через OIDC и SAML 2.0 посредством абстракции `IdentityProvider` (Okta, Microsoft Entra ID, Google Workspace, Keycloak, Auth0, любой OIDC-провайдер), провижининг (provisioning) и депровижининг пользователей через SCIM 2.0. Депровижининг отключает пользователя, отзывает его сессии и API-ключи (промпт §143).

**Машинные субъекты**
- API-ключи: формат `fvt_<12-char public id>_<32-byte random secret, base62>`. Сервер хранит префикс и HMAC-SHA256 секрета, вычисленный с серверным «перцем» (pepper), который хранится в конфигурации, а не в БД. Полный ключ показывается один раз. У ключей есть области действия (scopes — подмножества разрешений), срок действия (по умолчанию 90 дней, максимум настраивается), время и IP последнего использования; ключ можно мгновенно отозвать. Ключи, обнаруженные в формате gitleaks/GitHub secret scanning, позже можно будет отзывать автоматически через партнёрскую интеграцию со сканированием секретов.
- Сервисные аккаунты (фаза 9): нечеловеческие субъекты с собственными привязками ролей; их используют CI/CD, Terraform и GitOps.
- Воркеры аутентифицируются в PostgreSQL с собственными учётными данными. Идентификаторы экземпляров воркеров записываются в аренды (leases) и в аудит (`actor_type=system`).

## 4. Авторизация

- **Модель:** разрешения — это строки вида `resource:verb`. Роли — именованные наборы разрешений. Привязка роли (role binding) связывает роль с субъектом (пользователем, командой, сервисным аккаунтом, API-ключом) в определённой **области** (scope): организации, проекта или кластера. Привязка на уровне организации действует на все проекты и кластеры этой организации.
- **Встроенные роли (Community):**

| Роль | Кратко |
|---|---|
| Owner | Всё в организации, включая удаление организации, оплату/лицензию и управление ролями |
| Admin | Всё, кроме удаления организации и передачи владения |
| Operator | Создание, изменение, масштабирование и обновление кластеров, запуск операций, управление аддонами, узлами, резервными копиями; использование (но не чтение) учётных данных |
| Developer | Чтение кластеров и операций; скачивание kubeconfig (привязанного к пользователю); создание кластеров только в проектах/окружениях, разрешённых привязками (по умолчанию — development) |
| Viewer | Только чтение, без kubeconfig, без метаданных учётных данных, кроме имён |

- **Enterprise:** расширенный набор ролей по умолчанию из промпта §139 (Organization Owner, Organization Admin, Platform Admin, Cluster Admin, SRE, DevOps, Developer, Security Admin, Auditor, Viewer), **пользовательские роли** (промпт §140) и **условия ABAC**, которые движок политик вычисляет по атрибутам субъекта, ресурса и окружения (например, `project.environment == "development"`, `cluster.region == "eu"`, `cluster.ownerTeam in principal.teams`; промпт §141).
- **Применение:** единственный вызов `Authorizer.Authorize(principal, permission, resource)` в каждом методе прикладного сервиса до любых побочных эффектов. Обработчики не могут его пропустить, потому что сервисы принимают только контекст авторизованного типа. Каталог разрешений описывает каждое разрешение и эндпоинты, которые его используют. **Тесты матрицы авторизации** покрывают все сочетания «эндпоинт × роль × тенант».
- **Точки расширения для разделения обязанностей (ee):** процессы согласования гарантируют, что инициатор изменения в продакшене не может быть его единственным согласующим.
- **Использование учётных данных vs чтение:** использование учётных данных в операции (`credentials:use`) — это отдельное разрешение, не совпадающее с чтением их метаданных (`credentials:read`). Ни одно разрешение никогда не возвращает секретные данные.

## 5. Изоляция тенантов

- Каждая строка, принадлежащая тенанту, содержит `org_id` и, где это уместно, `project_id`. Каждый вызов репозитория требует `TenantScope`, который выводится из аутентифицированного субъекта после авторизации и никогда — только из данных, присланных клиентом.
- Политики PostgreSQL **RLS** на всех таблицах тенантов используют `current_setting('app.org_id')`, значение которого задаётся через `SET LOCAL` в каждой транзакции (см. [модель данных §4](../architecture/data-model.ru.md)). Роль приложения не может обойти RLS.
- Фоновые задания несут `org_id` и заново проверяют принадлежность каждого идентификатора, на который они ссылаются.
- Логи, аудит, события операций, секреты, kubeconfig и результаты поиска ограничены рамками тенанта. Потоки SSE проверяют авторизацию при подписке и при каждом возобновлённом подключении.
- Идентификаторы объектов невозможно угадать (в UUIDv7 74 случайных бита). Тем не менее для чужого или неизвестного идентификатора возвращается `404`, а не `403`, чтобы вызывающая сторона не могла перебирать ресурсы.
- Тесты: тесты на выход за пределы тенанта для каждого репозитория и каждого эндпоинта. Фаззинг с подстановкой идентификаторов в API-тестах.
- Никогда не полагаться на фронтенд в вопросах изоляции (промпт §212).

## 6. Управление секретами

### 6.1 Конвертное шифрование (промпт §85)

```
KEK  (key-encryption key)  — from KeyProvider: local key file / env (Community) | OpenBao/Vault Transit | AWS KMS | GCP KMS | Azure Key Vault (ee, BYOK)
 └── wraps  DEK (data-encryption key, 256-bit, per organization, versioned)  — stored wrapped in `data_keys`
       └── encrypts  secret payload with AES-256-GCM, random 96-bit nonce, AAD = org_id ‖ secret_id ‖ purpose  — stored in `secrets`
```

- **Привязка через AAD** не позволяет переносить шифротексты между тенантами, записями или назначениями (purpose). Если скопировать шифротекст в строку другой организации, расшифровка завершится ошибкой.
- **Безопасность nonce:** случайных 96-битных nonce под одним DEK хватает на гораздо большее число операций шифрования, чем одна организация когда-либо выполнит. DEK ротируются по расписанию (по умолчанию раз в год) или по запросу, что дополнительно ограничивает использование nonce.
- **Ротация:**
  - Ротация KEK лишь заново оборачивает DEK, и это дёшево.
  - Ротация DEK создаёт новый активный DEK. Новые записи используют его, а фоновое задание постепенно (lazily) перешифровывает старое содержимое. Старый DEK переходит в состояние `decrypt-only`, а после завершения перешифрования — в `destroyed`.
  - Ротация учётных данных (новый SSH-ключ или токен) — функция продукта с отслеживанием зависимых кластеров (промпт §169).
- **Реализация:** наборы ключей (keysets) Google Tink Go AEAD (AES-256-GCM) для каждой организации, зашифрованные AEAD на основе KEK. Ротация ключей внутри набора поддерживается штатно, а KMS-расширения Tink покрывают GCP KMS, AWS KMS и OpenBao/Vault Transit (ADR-0014). Никаких самописных криптографических примитивов; в CI выполняются тесты на известных ответах (known-answer tests).
- **Локальный KEK (Community):** 256-битный ключ из `ENCRYPTION_KEY` (base64) или из файла ключа (`ENCRYPTION_KEY_FILE`, рекомендуется; монтируется из Kubernetes Secret или файла с правами 0400). Без него сервер отказывается запускаться во всех профилях, кроме dev. Идентификатор и версия ключа записываются вместе с каждым обёрнутым DEK, поэтому во время ротации могут сосуществовать несколько KEK.
- **Внешние бэкенды (ee):** реализации `SecretBackend` могут хранить содержимое секретов в OpenBao/Vault KV или в облачных менеджерах секретов вместо PostgreSQL. Тогда строка `secrets` содержит только ссылку.

### 6.2 Правила обращения (промпт §25)

Учётные данные и секреты должны:
1. **храниться в зашифрованном виде**, как описано выше.
2. **никогда не попадать во фронтенд.** Секретные поля в API доступны только для записи. Ответы содержат метаданные: тип, отпечаток (например, `SHA256:…` для SSH-ключей), последние четыре символа токенов, время создания, ротации, последнего использования и срок действия.
3. **никогда не появляться в логах.** Маскировщик (redactor) скрывает каждое значение, полученное через `SecretAccessor`, во всём выводе логов и событий этой операции. Маскирование по шаблонам охватывает PEM-блоки, bearer-токены, пары `password=`/`token=` и `client-key-data` в kubeconfig. Структурированные поля из списка запрещённых (`password`, `token`, `secret`, `privateKey`, …) отбрасываются.
4. **никогда не появляться в сообщениях об ошибках.** Типизированные ошибки содержат коды и безопасные параметры. Исходные ошибки внешних систем (upstream) перед сохранением проходят через тот же маскировщик.
5. **никогда не попадать в git.** gitleaks запускается в CI и в pre-commit. Тестовые фикстуры используют сгенерированные одноразовые ключи. `.env` внесён в git-ignore, а `.env.example` содержит только заглушки.
6. **расшифровываться just-in-time**: только в памяти воркера и только для задачи, которой они нужны. Буферы с открытым текстом очищаются после использования (в Go — по мере возможности). Ключи никогда не записываются на диск. SSH-адаптер разбирает ключи в памяти, проброс агента (agent forwarding) по умолчанию отключён.

Канареечные тесты подкладывают в тестовые прогоны известные значения секретов, а затем ищут утечки в логах, событиях, ответах API и содержимом ошибок.

### 6.3 Секреты внутри управляемых кластеров

- Кластеры kubeadm настраиваются с **шифрованием Secrets при хранении (at rest)** (`EncryptionConfiguration`). По умолчанию используется локальный провайдер `aescbc`/`secretbox`, а при настроенном внешнем KMS — **KMS v2** (ee).
- Join-токены короткоживущие (по умолчанию 1 ч) и удаляются после операции. Ключи сертификатов kubeadm загружаются только на время присоединения узлов control plane.
- Административный kubeconfig хранится в зашифрованном виде и по умолчанию никогда не показывается в UI. Пользователи скачивают **короткоживущие kubeconfig, привязанные к пользователю**: клиентский сертификат, подписанный CA кластера, с TTL (по умолчанию 8 ч), а позже — OIDC. Каждое скачивание фиксируется в аудите.
- Закрытые ключи CA управляемых кластеров остаются на узлах control plane (поведение kubeadm по умолчанию). Платформа хранит их зашифрованную копию, только если пользователь включает «резервную копию PKI под управлением платформы» для аварийного восстановления. Ротация сертификатов выполняется как операция (промпт §29).

## 7. Безопасность удалённого выполнения (SSH, kubectl, Helm)

- **Никакой интерполяции в shell.** Удалённые команды — это списки argv (`Command{Program, Args}`). SSH-адаптер экранирует каждый аргумент строгими одинарными кавычками по правилам POSIX и запускает команду через `/bin/sh -c` исключительно как транспортную обёртку: за пределами экранированных аргументов нет текста, контролируемого пользователем. Правило линтера (собственный анализатор `go/analysis`) запрещает `exec.Command("sh", "-c", …)` и конкатенацию строк в `Command.Program` (промпт §116).
- **Проверенные входные данные.** Имена хостов (RFC 1123), IP/CIDR (`net/netip`), порты, имена/метки/taints Kubernetes, версии (только разрешённые через каталог), пути (префиксы из списка разрешённых), URL (список разрешённых схем, защита от SSRF). Валидаторы покрыты фаззинг-тестами.
- **Файлы через SFTP.** Конфигурация (kubeadm, containerd, sysctl, юниты systemd, манифест kube-vip) генерируется из типизированных структур Go, сериализуется полноценными энкодерами (YAML/TOML/INI) и загружается атомарно (временный файл + fsync + rename) с явно заданными владельцем и правами. Запись файлов через `echo`/heredoc не используется никогда.
- **Временный хелпер на узле (рекомендуется, фаза 3).** Слой начальной настройки (bootstrap) может загружать на время каждой операции небольшой подписанный статически скомпонованный бинарный хелпер. Он вызывается как `helper <step> < json-input` и выполняет сбор фактов, операции с файлами и пакетами со структурированными входом и выходом. Это устраняет различия между shell-утилитами дистрибутивов (например, Rust coreutils и `sudo-rs` в Ubuntu 26.04) и ещё больше сужает набор используемых команд. После операции хелпер удаляется (безагентная модель сохраняется). См. ADR-0015.
- **Ключи хостов.** Неизвестные ключи хостов никогда не принимаются молча. Пользователь подтверждает отпечаток (или предоставляет known_hosts/SSH CA), и он сохраняется в `ssh_known_hosts`. При несовпадении операция останавливается с ошибкой `SSH_HOST_KEY_MISMATCH`.
- **Привилегии.** `sudo -n` используется только для отдельных шагов, вход под root не требуется, а документация рекомендует выделенного пользователя для провижининга с ограниченным sudo.
- **Kubernetes API.** client-go с закреплённым (pinned) CA кластера. Server-side apply с выделенным field manager. RBAC внутрикластерной учётной записи платформы ограничен тем, что нужно для управления аддонами.
- **Helm.** Встроенный SDK (без shell). Чарты берутся только по закреплённым в каталоге ссылкам с digest. Пользовательские переопределения values — это структурированные данные, проверяемые по схеме чарта, и никогда не текст шаблонов.
- **YAML от пользователя.** Строгое декодирование (неизвестные поля — ошибка), ограничение размера (по умолчанию 1 MiB), ограничение раскрытия алиасов/якорей (защита от billion laughs), максимальная глубина вложенности, затем валидация по JSON Schema. «Расширенные» (advanced) патчи ClusterSpec ограничены задокументированными полями конфигурации kubeadm/kubelet/containerd.

## 8. Сетевая безопасность платформы

- **TLS** на всех внешних listener (TLS 1.2+, современные наборы шифров; предпочтительно TLS 1.3). Встроенный сервер может использовать предоставленные сертификаты или работать за прокси, терминирующим TLS; при прямой отдаче HTTPS включается HSTS.
- **PostgreSQL** через TLS с `verify-full` в профилях для продакшена.
- **Защита от SSRF** (`internal/adapters/httpx`) для каждого исходящего запроса на URL, на который может влиять пользователь: вебхуки, Helm/OCI-репозитории, Git, реестры, OIDC discovery, эндпоинты уведомлений. Она:
  - разрешает имя через DNS, а затем подключается к полученному IP (без TOCTOU);
  - блокирует loopback, link-local, multicast, unspecified, частные диапазоны (с настраиваемым списком разрешённых для self-hosted установок, которым они нужны), эндпоинты метаданных облаков (`169.254.169.254`, `fd00:ec2::254`, `metadata.google.internal`, …);
  - повторяет проверку при каждом редиректе (не более 3);
  - применяет список разрешённых схем (`https`, а `http` — только если он явно разрешён), тайм-ауты и ограничения размера ответа.
- **Обход путей (path traversal):** файлы отдаются только для встроенного веб-интерфейса (`embed.FS`, без доступа к файловой системе). При распаковке архивов (офлайн-бандлы, кеш Helm-чартов) проверяются `..`, абсолютные пути и символические ссылки.
- **Ограничение частоты запросов (rate limiting)** по пользователю, API-ключу, организации и IP; отдельные, более строгие лимиты для входа, плана, предварительных проверок (preflight) и kubeconfig.
- **Заголовки безопасности:** CSP (`default-src 'self'`, без inline-скриптов, `frame-ancestors 'none'`), `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, минимальный `Permissions-Policy`.
- **Эндпоинты метрик и отладки** работают на отдельном listener, привязанном к localhost или к сети подов, и никогда — на публичном порту.

## 9. Аудит

- Записываемые действия (промпт §118, §156): аутентификация (успех/неудача), отказы в авторизации, создание/изменение/удаление/обновление/масштабирование кластеров, резервное копирование/восстановление, установка/удаление аддонов, действия с узлами, скачивание kubeconfig, создание/ротация/удаление/использование учётных данных, изменения ролей и привязок, изменения пользователей, жизненный цикл API-ключей, изменения вебхуков, изменения политик и согласования (ee), изменения настроек.
- Каждое событие фиксирует, **кто** (тип актора, идентификатор и отображаемое имя на тот момент), **что** (действие), **когда** (метка времени сервера), **откуда** (IP, user agent, идентификатор запроса), **цель** (тип, идентификатор, проект, кластер), **результат** (success / failure / denied) и **подробности** (замаскированные, например краткая сводка diff спецификации).
- Целостность: `audit_events` — таблица только для добавления (append-only). У роли приложения есть только `INSERT`, без `UPDATE`/`DELETE`. Строки **связаны в хеш-цепочку в пределах каждой организации**, а задание проверки и эндпоинт API выявляют подделку. Срок хранения обеспечивается удалением партиций после экспорта (настраивается; в Enterprise — блокировка политики хранения (retention lock)).
- Экспорт: JSON и CSV в Community. Вебхук SIEM, syslog (RFC 5424 поверх TLS), S3, Splunk, Datadog, Elastic и Sentinel в Enterprise (промпт §158).

## 10. Безопасность управляемых кластеров (что настраивает платформа)

Профили для продакшена и «усиленный» (hardened) профиль включают:

| Область | По умолчанию в усиленном профиле |
|---|---|
| Pod Security Admission | `restricted` в режиме enforce для пользовательских namespace, `baseline` в режимах audit/warn для всего кластера; системные namespace явно исключены |
| NetworkPolicies | Предлагается шаблон default-deny для каждого namespace; для продакшена обязателен CNI с поддержкой политик |
| API server | Анонимная аутентификация ограничена эндпоинтами health, журнал аудита с разумной политикой, шифрование секретов при хранении, admission-плагины (NodeRestriction и др.), профилирование отключено |
| Kubelet | Аутентификация/авторизация через webhook, read-only порт отключён, ротация сертификатов, protect kernel defaults |
| etcd | Аутентификация пиров и клиентов по TLS (по умолчанию в kubeadm), снапшоты зашифрованы при хранении в целевом хранилище резервных копий |
| Сертификаты | cert-manager для TLS рабочих нагрузок (Let's Encrypt HTTP-01/DNS-01, внутренний CA, существующие, самоподписанные), мониторинг срока действия сертификатов control plane |
| RBAC | По умолчанию никаких привязок cluster-admin для пользователей; пользовательские kubeconfig сопоставлены с группами по принципу минимальных привилегий |
| Политика образов (позже/ee) | Разрешённые/заблокированные реестры, проверка подписей (Kyverno `verifyImages`/Sigstore), частный реестр по умолчанию |
| Сканирование (позже/ee) | kube-bench / Kubescape для CIS benchmark, Trivy Operator для поиска уязвимостей, оценка уровня защищённости (security posture) для каждого кластера |

Платформа никогда не заявляет, что кластер «соответствует» какому-либо стандарту. Она сообщает о мерах контроля, их статусе, доказательствах и рекомендациях (промпт §160).

## 11. Безопасность цепочки поставок и релизов

- Зависимости зафиксированы: `go.sum`, lock-файл pnpm и GitHub Actions, закреплённые по полному SHA коммита. Renovate/Dependabot открывают PR с обновлениями, и каждое обновление проходит полный набор тестов.
- Обязательные проверки безопасности в CI: `govulncheck`, OSV-Scanner/Grype для зависимостей, сканирование образов (выбор сканера — в ADR-0019), gitleaks, статический анализ (правила gosec в golangci-lint, правила безопасности ESLint), проверка лицензионной политики.
- Артефакты релиза получают контрольные суммы, **подписи cosign в режиме keyless** (Sigstore, GitHub OIDC), **SBOM** (SPDX или CycloneDX, генерируется Syft), аттестации **SLSA provenance**, метаданные версии и сборки (промпт §226). Цель — воспроизводимые сборки (`-trimpath`, закреплённый тулчейн, `SOURCE_DATE_EPOCH`).
- Содержимое каталога (чарты, образы, бинарные файлы для узлов) закреплено по digest/контрольной сумме и проверяется при использовании. Офлайн-бандлы снабжаются подписями и контрольными суммами и проверяются при импорте.
- Образы контейнеров: минимальные (distroless/static), UID не root, корневая файловая система только для чтения, без shell, `HEALTHCHECK` там, где среда выполнения это поддерживает, без тегов `latest` (промпт §79).

## 12. Эксплуатационная безопасность

- **Конфигурация:** все секреты передаются через файлы или переменные окружения (`DATABASE_URL`, `ENCRYPTION_KEY_FILE`, `SESSION_SECRET_FILE`, `API_KEY_PEPPER_FILE`, …). `.env.example` задокументирован. Сервер проверяет конфигурацию при запуске и в профилях для продакшена отказывается работать с небезопасными сочетаниями настроек (отсутствует KEK, незашифрованное подключение к БД, режим отладки).
- **Логирование:** структурированный JSON (`slog`), идентификаторы запросов, никаких секретов, никаких полных тел запросов для чувствительных эндпоинтов.
- **Резервное копирование платформы:** база данных (включая зашифрованные секреты), конфигурация, журналы аудита. Резервные копии KEK хранятся **отдельно** от резервных копий базы данных. Тесты восстановления входят в чек-лист релиза (промпт §183).
- **Раскрытие уязвимостей:** `SECURITY.md` (фаза 1) с закрытым каналом для сообщений, списком поддерживаемых версий и целевыми сроками реакции.
- **Модель угроз** ведётся в [THREAT_MODEL.ru.md](THREAT_MODEL.ru.md) и пересматривается на каждой контрольной точке фазы. Новые функции, затрагивающие учётные данные, мультитенантность, удалённое выполнение или исходящий сетевой доступ, требуют обновления модели угроз в том же PR.
